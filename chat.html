Case 3 · Buyer and seller chat

Listen to this chapter →

A buyer asks whether a bicycle is available. A duplicate message is annoying; acknowledging a message and then losing it damages trust. This case separates durable acceptance, delivery, reading, and connection state.

Exact interview prompt

Design one-to-one buyer–seller messaging for Corner Market, including offline delivery, retries, read receipts, and multiple devices. Explain what “message sent” means during failures.

Clarifying questions and assumed answers

Assume private conversations between two members, text plus references to previously scanned attachments, history retained for one year, and no large group chat. End-to-end encryption is a possible later product requirement, not silently promised by transport encryption. Ask whether edited messages and deletion are required; support tombstone deletion but defer editing. Messages need order within one conversation; no global order across all conversations. Presence can be stale and must not authorize access.

Set durable-send acknowledgment p95 under 300 ms, online delivery p95 under one second under healthy conditions, and 99.95% monthly send availability. Acknowledgment means committed to the chosen durable replicated store. “Delivered” means at least one recipient device acknowledged receipt; “read” means the user explicitly advanced a read position. State that replication policy determines the remaining loss window after a regional disaster. Do not imply that a successful network write is durable storage.

Calculate load and connection resources

Assume 200,000 daily messaging users sending 20 messages each: 4 million messages/day, or 46.3/s average and 463/s at a 10× assumed peak. At 1,000 logical bytes/message, history adds 4 GB/day and 1.46 TB/year before indexes and replicas. Attachment bytes live in object storage and are excluded. Suppose 50,000 simultaneous devices hold connections; at an assumed 20 KB application state each, that is 1 GB of connection state across gateways, excluding operating-system socket buffers and runtime overhead.

With one heartbeat every 30 seconds/device, the service handles about 1,667 heartbeat sends/s and corresponding replies. Heartbeats can exceed average message traffic. Capacity testing must include reconnect storms, TLS handshakes, slow consumers, and file-descriptor limits. TLS is transport layer security, which encrypts a connection; it does not encrypt data from the service itself.

API and storage contract

POST /v1/conversations/{id}/messages
{ client_message_id, text, attachment_ids }
→ { message_id, sequence, accepted_at }
GET /v1/conversations/{id}/messages?after_sequence=123&limit=50
PUT /v1/conversations/{id}/read-position { sequence: 130 }
WebSocket events: message_available, delivery_receipt, presence_hint

conversations(id PRIMARY KEY, member_a, member_b, next_sequence)
messages(conversation_id, sequence, message_id, sender_id,
         client_message_id, payload, created_at, status,
         PRIMARY KEY(conversation_id, sequence),
         UNIQUE(conversation_id, sender_id, client_message_id))
read_positions(conversation_id, user_id, sequence)
outbox(event_id PRIMARY KEY, conversation_id, sequence)

A WebSocket is a persistent bidirectional connection established through an HTTP handshake. It reduces repeated connection overhead but provides no durable history by itself. The same logical send endpoint can be exposed over HTTP or a socket command; it must enforce identical authorization and deduplication.

Offline/reconnect → history API → durable messages after cursor

Begin with HTTP sends and polling history. For each send, check current membership, then lock/update the conversation row and allocate its next sequence in the same transaction as insertion. This gives one authoritative order per conversation, not a wall-clock guess. A retry with the same client_message_id returns the existing result; different payload with that ID is conflict. A rollback must roll back allocation too, although clients should not assume every system promises gap-free sequences.

Add a transactional outbox and delivery workers, then connection gateways when polling cost or latency justifies them. Gateway registration maps a device to its current gateway with an expiry and connection generation. The durable store remains authoritative. After reconnect, the client fetches messages after its last stored sequence, even if the gateway believes nothing was missed.

Ordering, duplicates, and receipts

Delivery is at least once: messages may repeat after retries. Devices merge by stable message_id or conversation sequence and render one copy. Concurrent sends from two devices receive an order at the authoritative conversation owner. If sequence 132 arrives before 131, buffer briefly or fetch the missing range; do not reorder by client timestamps, which can be inaccurate or manipulated. A single busy conversation is serialized by design. Partitioning by conversation_id scales many conversations, but does not make one conversation infinitely scalable.

Read position updates are monotonic: store max(existing, requested), after verifying the position belongs to that conversation and is valid. A slow device cannot move it backward. Delivery and read receipts are separate: receiving a background push notification does not prove reading. Push notification payloads should avoid private message bodies unless product privacy policy explicitly permits them.

Failure analysis

If commit succeeds but the response is lost, the client retries its original ID and receives the original sequence. If a worker sends an event then crashes, replay produces a duplicate event, which devices tolerate. If a gateway dies, messages are still durable and reconnect history fills the gap. If a device is slow, bound its send buffer and disconnect with a resumable cursor rather than allowing unbounded memory growth.

When database quorum is unavailable, do not acknowledge durable acceptance. Quorum is the required number of replicas participating in an operation under the selected replication scheme. A gateway may keep a local optimistic message marked “sending,” but must not label it committed. For blocked or removed members, recheck membership before history reads and sends; transport connection authentication from ten minutes ago is insufficient. Rate limits and spam controls should apply per sender and conversation, with explicit rejection rather than silently dropped accepted messages.

Alternatives, cost, and evolution

Reject “use WebSockets and Redis Pub/Sub” as a complete design: transient delivery alone cannot recover offline history. Reject global sequence allocation because unrelated conversations do not require shared ordering. Client-generated timestamps are useful metadata but unsuitable as the sole ordering authority. A single SQL store may be sufficient at this assumed write rate; partition based on measured storage and query pressure, not messaging fashion.

For multi-region service, start with one home region per conversation and route writes there. Regional failover needs a fencing epoch, a version proving which owner is allowed to write, plus a documented recovery point and replay strategy. Active writers in two regions cannot casually promise one strict sequence during a partition. Encryption key custody, user export/deletion, moderation access, and audit retention require product decisions before claiming end-to-end encryption.

Track acceptance latency and error rate, oldest undelivered event, reconnect gap recovery, gateway connection count, buffer pressure, and deduplication rate. Test deleting a gateway mid-send and losing a response after commit. Sample content-free traces using message IDs and protect metadata because communication patterns can themselves be sensitive.

Follow-ups and rubric

Practice: can you guarantee exactly one notification and exactly one stored message?

A database uniqueness constraint can ensure one stored logical message per idempotency key. External push effects can duplicate across ambiguous retries unless the provider supports equivalent deduplication. State the boundary instead of promising universal exactly-once behavior.

Practice: a recipient comes online after seven days.

Fetch durable history from the saved sequence in bounded pages, then merge live events with deduplication. A connection registry or transient queue is not the history source.

Strong: states acceptance semantics, handles ambiguous commit and reconnect, and distinguishes device delivery from read state. Weak: equates an open socket with reliability, orders by wall clocks, or loses offline messages. Principal depth includes failover fencing, abuse policy, and privacy implications of encryption choices.

Technical references checked 2026-10-19: WebSocket protocol, RFC 6455; PostgreSQL constraints. Durability and failover guarantees depend on the selected deployment configuration.

A short spoken walkthrough

Candidate: Does sent mean accepted by our database or shown on the recipient device?
Interviewer: Accepted durably by the service.
Candidate: I will start with the simplest durable path and state the boundary before distributing it.
Interviewer: The socket connection dies immediately after commit. Do you send a second message?
Candidate: The client retries its stable message ID. The conversation uniqueness constraint returns the existing committed sequence. Delivery retries can repeat frames, so the recipient deduplicates by message identity and resumes from its last durable cursor. I would label delivered and read as separate states rather than misrepresenting the durable acknowledgment.
