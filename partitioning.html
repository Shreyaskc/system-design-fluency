7. Partition by ownership, queries, and skew

Partition only when there is a pressure

Partitioning divides a dataset into subsets. Sharding usually means placing subsets on independently managed database nodes. A table partition inside one database can simplify retention without independently scaling every resource. Corner Market's baseline order volume does not itself justify sharding. First improve queries, indexes, archival, connection management, and vertical capacity. Partition when storage, write throughput, operational isolation, or geographic ownership has a measured requirement that one node cannot economically satisfy.

A partition key decides where a record belongs. Choosing store identifier keeps a store's inventory and reservations together, helping local transactions. Choosing shopper identifier makes shopper history local, but a checkout touching several stores may cross shards. Choosing random order identifier spreads writes while forcing shopper history to consult an index or multiple shards. There is no universally correct key: list the important reads, writes, transaction boundaries, and expected skew before choosing.

Hash and range placement

Hash partitioning maps a key through a function to a partition, tending to spread many unrelated keys. Range partitioning groups ordered values, helping range scans and time-based retention but risking concentrated writes to the newest range. A mapping such as hash(key) modulo node count is simple, yet changing node count remaps many keys. A directory or stable logical bucket layer decouples records from physical nodes: hash into 1,024 logical buckets, then map buckets to servers.

At an illustrative 2 TB dataset and 1,024 uniformly populated buckets, each bucket averages approximately 1.95 GB using decimal units. Moving sixteen buckets moves about 31.25 GB on average. Actual bucket sizes and hotness can differ dramatically. Keep both byte and request metrics per bucket; equal storage does not imply equal compute demand. Stable hashing is a placement aid, not proof that the workload is balanced.

Hot keys need a separate answer

Suppose one celebrity grocer receives forty percent of all traffic. With sixteen shards, a store-key scheme still concentrates that traffic on one shard. A hot key is a single identifier with excessive demand; a hot partition can contain many individually ordinary keys. Cache immutable reads, split large stores into item groups, or isolate the tenant. A single inventory item's strict stock counter remains a contention point unless the product supports quota allocation or queued admission.

Salting appends a random or chosen suffix to spread writes. It helps independent events because readers can aggregate across suffixes. It complicates unique constraints, ordered pagination, and atomic counters. “Salt the key” is therefore incomplete for stock: independently decrementing several counters requires safe initial allocation and rules for transferring unused quantity. Global unique usernames similarly need a coordinating namespace or a uniqueness mechanism beyond local shard constraints.

Reshard without guessing ownership

A migration must decide which location may accept writes at every moment. One workable outline creates a target copy, streams subsequent source changes, verifies counts and checksums at a known log position, briefly fences or redirects writes, catches up the target, then switches the routing directory version. Retain a rollback window. A dual-write phase without a durable reconciliation mechanism can leave source and target divergent whenever one write succeeds and the other fails.

Routing clients should learn a mapping version and handle stale routes through a bounded redirect or retry. Move requests with their idempotency identity so a retry crossing the cutover cannot create duplicate reservations. Monitor both missing records and duplicated effects. Checksums of a whole dataset may conceal which range diverged; compare per-range or per-bucket summaries and sample semantic queries as well.

Cross-shard behavior and privacy

A cross-shard join combines records stored under different owners. It can require fan-out and merging, which increases network work and exposes the request to more failures. Maintain a derived shopper-order index when that view is important, accepting and measuring its lag. A distributed transaction can preserve atomicity across participants but adds coordination and failure handling. A saga instead records a sequence of local steps with compensating actions; compensation is a business action and may not perfectly undo an external effect.

Deleting a shopper's data now requires discovering authoritative rows, replicas, caches, derived indexes, exports, and backup retention policies. A shard directory is operational infrastructure whose loss can make otherwise healthy data unreachable. Back up mappings, test rebuilding them, and constrain tenant access so an incorrect key cannot route a shopper into another tenant's dataset.

Practice: choose a shard key for inventory and explain one rejected alternative.

Start with store identifier if most reservations and replenishment are store-local. Reject shopper identifier for authoritative inventory because independent shoppers contend on the same store-item stock. Keep a separate shopper-order projection for history. Revisit the choice when a single store exceeds a shard's capacity, using item groups or explicit allocations rather than assuming more shards fix one hot item.

Exit artifact: draw ownership before, during, and after moving one bucket. Identify the only accepted writer in each phase and show how a stale client recovers without duplicating an effect.

Request trace: One owner per bucket

A reserve request hashes store s7 to bucket seventeen; routing version eight points to server B; B performs the local transaction. A stale router sends to A after cutover; A must reject or redirect rather than write. This ownership check is essential even if both databases contain apparently complete copies.
