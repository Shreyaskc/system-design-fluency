Interfaces, contract, and flow.

The recommendation endpoint accepts a context and limit, returning items, a request identifier, the model version, and an optional fallback reason. Feature definitions specify names, types, entity keys, transformation versions, event-time meaning, freshness limits, and defaults. Online feature rows are keyed by entity and feature-set version, and record source event time, computation time, and expiry separately. The model manifest declares its required feature set, schema hash, artifact digest, and rollout policy. Exposure events record candidates, displayed items, model version, and experiment assignment. These fields make compatibility, freshness, reproducibility, and later evaluation inspectable rather than implicit.

A model manifest declares the required inputs; deployments must reject incompatible feature versions. Do not expose unnecessary user features in the client response. An exposure event records what the user actually saw, so offline evaluation can distinguish unseen candidates from displayed results. Restrict access to feature data and bound retention independently for raw events, derived features, and experiment logs.

Interaction events enter versioned transformations that populate historical and online feature stores. Historical features support point-in-time-correct training, followed by model validation and registration of a versioned artifact. Materialization prepares compatible online features. During serving, a request first retrieves candidates, then performs a batched feature lookup before model inference. A current eligibility filter runs after scoring so stale features cannot authorize a now-forbidden item. Finally, the system returns a ranked response or a popular-items fallback. The parallel training and serving paths must agree on feature meaning and versions; sharing a name alone does not prevent training-serving skew.
