LESSON 17 / 27 · ORIGINAL TEACHING EXAMPLES

Case 4 · Reliable listing photos and video

Listen to this chapter →

A seller uploads a bicycle video over an unreliable mobile connection. Media bytes need a separate data path from control metadata. This case trains resumability, asynchronous state machines, authorization, and cost reasoning.

Exact interview prompt

Design photo and short-video uploads for Corner Market. Uploads must resume after network interruption, files must be checked before publication, and popular listings should load quickly.

Clarifications and assumed requirements

Ask maximum size, formats, privacy, processing needs, and freshness. Assume 100,000 uploads/day, average original size 20 MB, maximum 500 MB, public listing media after validation, and one original plus resized/transcoded outputs. Do not make private chat attachments publicly accessible by reusing this policy. Upload completion can precede readiness; processing p95 under two minutes for supported files is a proposed target requiring benchmarking. Metadata API availability objective is 99.9% monthly. A successful upload means durable original bytes verified by the service; “ready” additionally means checks and transformations succeeded.

Use decimal MB and GB. Average ingress is 100,000 × 20 MB = 2 TB/day, or about 23.15 MB/s; assumed 10× peak is 231.5 MB/s before overhead. At 30 days original retention, originals total 60 TB. Assume all generated outputs add 50% of original bytes: 1 TB/day and 30 TB retained, giving 90 TB logical media storage before replicas and versioning. If each upload generates 50 views and each view transfers an assumed 1 MB, delivery is 5 TB/day. Transfer and transcoding can dominate metadata cost.

Contract and data model

POST /v1/uploads { filename, declared_size, media_type, checksum }
→ { upload_id, expires_at, part_size, signed_part_urls }
POST /v1/uploads/{id}/complete { parts: [{ number, checksum, token }] }
→ 202 { state: "verifying" }
GET /v1/uploads/{id} → { state, reason_code, ready_variants }
DELETE /v1/uploads/{id} → cancellation request

uploads(id PRIMARY KEY, owner_id, storage_key UNIQUE,
        declared_size, actual_size, checksum, state, version, expires_at)
variants(upload_id, kind, object_key, checksum,
         UNIQUE(upload_id, kind))
processing_jobs(upload_id, pipeline_version, state, attempt,
                UNIQUE(upload_id, pipeline_version))

A signed upload URL grants time-limited permission for a specific storage operation. It is a bearer capability: whoever holds it can exercise its permission. Do not put it in analytics logs. An unpredictable object key and restricted creator permissions reduce exposure but do not replace ownership checks in the control API.

Labeled data and control paths

CONTROL: Seller → upload API/auth → upload metadata database
                                  → short-lived scoped upload URLs
BYTES:   Seller ── multipart data ─→ private quarantine object storage
COMPLETE: API → verify object/parts → state + durable processing event
PROCESS: queue → isolated scanner/decoder → resize/transcode workers
                         ↓ failure             ↓ success
                      rejected             publish ready variants
READ:    Viewer → content delivery network → ready object storage

Progressive design

Start with a single object upload for small images and a metadata row. Keep originals in a private quarantine location. Add multipart upload for large or unreliable transfers: divide the object into separately retryable parts, then complete assembly. With a 10 MB chosen part size, a 500 MB object has 50 parts. A failure on part 49 need not resend the preceding 480 MB. Keep concurrency bounded so one upload does not overwhelm mobile bandwidth or create excessive requests.

The API allocates the storage key, records owner, expected size, checksum, and expiry, then signs only necessary operations. On completion, verify actual stored size, checksum semantics, upload ownership, and all expected parts. An object-storage ETag is not universally a whole-file cryptographic checksum, particularly for multipart objects; use an explicitly supported checksum mechanism. Server verification must not trust a client's declaration that a file is an image.

Use a state machine: initiated → uploading → verifying → processing → ready, with rejected, expired, and cancelled terminal states. A state machine explicitly defines allowed transitions. Apply conditional updates using a version so a late worker cannot publish a cancelled upload. Repeated completion returns the current state. A persistent outbox or reconciler closes the gap between marking verified and scheduling processing; database and object storage do not share one ordinary transaction.

Processing and delivery deep dives

Workers identify actual formats, enforce decoded pixel/frame/duration limits, scan as appropriate, and run parsers in resource-limited isolated environments. A small compressed file can expand into enormous memory. Never execute uploaded content or trust filenames. Produce immutable output keys incorporating upload ID and pipeline version. Retrying a job can safely overwrite only its own deterministic unpublished output or detect an already verified output; publication is a conditional metadata transition.

A content delivery network (CDN) caches objects near viewers. Use immutable versioned paths and long cache lifetimes for public ready variants. Deleting metadata alone does not purge a CDN, so define takedown propagation and purge operations. For restricted media, use an authenticated delivery mechanism with bounded signed access lifetimes and explicit cache rules. Do not assume the listing page's login protects a publicly addressable object.

Failure analysis

If a client disappears, a lifecycle rule or sweeper aborts abandoned multipart uploads and expires metadata after a documented window. Otherwise uploaded parts can accumulate cost indefinitely. If completion succeeds but its response is lost, retry queries current state; do not allocate a second object. If the worker queue is delayed, show processing status and backlog age rather than publishing unchecked bytes. If a worker crashes after writing output but before state transition, retry validates existing output and completes the transition.

If the metadata database fails after object creation, reconciliation finds orphan objects using a bounded inventory process and deletes only after a grace period. If storage emits duplicate or out-of-order notifications, deduplicate by upload and pipeline version, and verify current state before processing. Notifications are hints to inspect durable state, not proof of readiness. Cancellation and publication must contend through the same conditional transition to prevent a race.

Alternatives and evolution

Proxying every byte through the application server simplifies a tiny prototype but ties API scaling to bandwidth and long-lived requests. Direct-to-storage uploads avoid that bottleneck while requiring careful capability scoping. Reject synchronous scanning in the upload request for large videos because processing time and retries exceed ordinary request budgets. Reject storing media blobs in the primary relational database for this workload unless an unusual transactional requirement outweighs backup and serving costs.

Monitor completion rate by device/network, orphan bytes, incomplete upload age, scanner failures, processing backlog age, cost per ready minute of video, CDN hit ratio, and origin traffic. Avoid auto-scaling solely on queue length: a 500 MB video costs more than a small image; measure work units and memory pressure. Add adaptive video formats only after device support and viewing behavior justify them. Regional upload acceleration is a latency/cost choice to benchmark, not a default requirement.

Follow-ups and rubric

Practice: an upload URL leaks before expiry. Can you call it single use?

Not by default. The exact storage capability may be reusable while valid. Use short expiry, narrowly scoped keys and permissions, controlled finalization, and explicit provider-supported conditional mechanisms where required. Do not promise revocation that the chosen capability cannot enforce.

Practice: moderation rejects an already popular published file.

Set authoritative status to removed, stop issuing access, purge caches, remove ready references, and record purge completion against the takedown objective. Existing downloaded copies cannot be recalled.

Strong: separates accepted bytes from ready media, designs idempotent state transitions, verifies content, and budgets orphan/egress cost. Weak: treats a client completion call or storage event as proof of safety, publishes originals immediately, or assumes a signed URL is single use. Principal depth includes parser isolation, reconciliation ownership, and takedown guarantees.

Technical references checked 2026-10-19: S3 multipart upload; S3 signed URL behavior. AWS is a concrete example; verify limits and checksum behavior for the chosen storage provider.

A short spoken walkthrough

Candidate: Can an upload be visible before validation completes?
Interviewer: No; only verified and scanned media may be published.
Candidate: I will start with the simplest durable path and state the boundary before distributing it.
Interviewer: The object exists but finalize timed out. Should the client upload it again?
Candidate: First retry finalize with the existing upload ID. The service checks object identity, size and checksum and conditionally advances metadata. A stored object alone is not publication authority. Cleanup uses an age threshold and state check so it does not erase an active upload; validation workers remain idempotent.
