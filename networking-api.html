3. Follow a request and design a durable API

Trace the path

A network request crosses independently failing boundaries. The shopper's client resolves a hostname using the DNS, establishes a transport connection, negotiates TLS, and sends an HTTP request. A load balancer distributes requests among healthy application instances. Connection reuse avoids repeating setup for every request, but a broken reused connection still needs bounded recovery. A server marked healthy may have a failing database, so distinguish process liveness from readiness to accept useful traffic.

Latency is elapsed time for one operation; throughput is completed operations per unit time. Greater bandwidth does not remove a long round trip. Four sequential dependent calls across a 70-millisecond path spend at least 280 milliseconds on those trips before processing. Batch independent lookups, colocate related operations, or redesign a chatty interface. Parallel calls help independent work but create additional load and complicate cancellation when the parent request no longer needs results.

A reservation contract

Expose POST /v1/reservations with a client-generated Idempotency-Key, authenticated shopper identity, store identifier, item identifier, quantity, and expected price version. An idempotent effect means repeating an operation does not multiply its intended state change. This endpoint implements that property through a stored key scoped to the shopper and operation; merely naming a header does not provide it. Save a hash of the request body so reuse with different content is rejected.

POST /v1/reservations
Idempotency-Key: 7f2-example
{"store_id":"s7","item_id":"apple","quantity":3,"price_version":12}

201 Created
{"reservation_id":"r81","state":"held","expires_at":"...","version":1}

The schema is deliberately small. Quantity must be a positive bounded integer. Price is checked against a server-owned version. The response contains a stable identifier that GET /v1/reservations/r81 can retrieve after a timeout. The key table stores shopper, operation, key, body hash, result identifier, and expiration. Commit the key and reservation together. Retain keys for the documented retry window; clients cannot assume protection after keys expire.

Errors are part of the interface

Return a structured error with a machine-readable code, human-readable message, request identifier, and retry guidance. Distinguish invalid quantity, unavailable stock, authorization failure, and temporary dependency failure. HTTP defines method and status semantics; for example, GET is safe, and PUT and DELETE have idempotent semantics, while POST is not inherently idempotent. Those properties concern intended server effects, not whether every repeated response has identical bytes. See RFC 9110, checked 2026-10-19.

A timeout tells the client it stopped waiting; it does not prove the server failed. Set a total request deadline and allocate smaller dependency timeouts within it. If a 500-millisecond server deadline allows a database call to wait two seconds, the work outlives its purpose. Propagate cancellation where supported, but preserve a committed operation's retrievable outcome. Retry only operations whose effects are safe to repeat, with a limited attempt count, increasing delay, and randomness to avoid synchronized retries.

Pagination, compatibility, and trust

For order history, sort by (created_at, order_id) and return an opaque cursor containing the last pair. Keyset pagination resumes from the last observed key; offset pagination skips a count of rows and can become expensive or unstable when new rows arrive. Define whether a browsing session sees a fixed snapshot or a changing history. Always add a unique tiebreaker because timestamps can coincide.

Authentication establishes identity; authorization decides whether that identity may perform this operation on this object. Never accept a supplied shopper identifier as proof of ownership. Enforce authorization on each retrieved reservation and each mutation. Bound body sizes, item counts, and query complexity. Avoid putting secrets in URLs because URLs often enter logs. Version contracts by making additive changes first; removing a field requires evidence that old clients no longer depend on it.

Practice: POST times out, then the client retries with a new key. What breaks?

The server may interpret the retry as a second operation and hold stock twice. Retry with the same key and unchanged body, or retrieve the original result. If the original key is unknown because local client state was lost, show pending status and reconcile rather than claiming the first attempt failed.

Exit artifact: document one success, one business rejection, one authentication failure, and one uncertain outcome. Draw the entire request path and label every place a deadline, identity, or identifier must survive.

Predict an uncertain external outcome

Payment sequence: the client creates attempt P7; the service sends capture P7; the provider captures money; the response is lost; the local deadline expires. “Failed” is now an incorrect conclusion because the effect occurred. Store P7 as pending, retrieve provider status or retry under the provider's documented idempotency contract, then reconcile the order. The invariant is one successful capture per order. A local database rollback cannot roll back the provider.

Debug: would a longer timeout remove this failure mode?

No. It changes probability and waiting cost, but any finite deadline can expire after an effect occurs. Durable attempt identity and reconciliation address ambiguity.
