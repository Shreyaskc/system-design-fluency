LESSON 25 / 27 · ORIGINAL TEACHING EXAMPLES

Case 12 · Defend inventory across regions

Corner Market expands internationally. Regional independence sounds attractive until two buyers reserve the final bicycle during a network partition. This capstone makes the availability, latency, and correctness contract explicit.

Exact interview prompt

Design multi-region inventory reservation at 20,000 peak reads/s and 2,000 peak writes/s. Prevent overselling, target zero loss of acknowledged writes and recovery within five minutes, and explain regional failure behavior.

Clarification dialogue and objectives

Candidate: “Does zero loss mean any single regional failure, and can a partitioned minority reject writes?” Interviewer: “Yes. Single-region failure is the fault model. No overselling; reads may be stale.” Candidate: “I will require durable cross-region quorum before acknowledging a write. I cannot also promise every isolated region accepts writes.”

Recovery point objective (RPO) is the allowed loss of acknowledged data; assume RPO 0 for a single-region failure under the stated durable quorum model. Recovery time objective (RTO) is the time to restore the specified service; target under five minutes, demonstrated through exercises. These objectives do not cover destruction of every copy, operator corruption without recoverable history, or arbitrary simultaneous regional failures. Define the fault model before claiming a guarantee.

Assume 99.95% monthly time-based write availability. Over a 30-day month, the error budget is 30 × 24 × 60 × 0.0005 = 21.6 minutes. A four-minute incident would consume about 18.5% of that budget. This is a time-based simplification; a request-based service-level indicator measures failed eligible requests instead. Reads target p95 under 100 ms from local derived views, with explicit freshness. Writes have a separate latency budget.

Latency and capacity reasoning

Assume hypothetical 80 ms inter-region round-trip time (RTT), meaning a request and response across regions take 80 ms before durable storage and processing. A coordinated write requiring that exchange cannot achieve a 50 ms response under those assumptions. Negotiate a feasible write objective, for example p95 under 250 ms subject to measurements. Parallel local processing does not remove the communication lower bound. Actual topology and consensus protocol determine the precise path.

At 2,000 writes/s and assumed 250 ms average in-flight duration, Little's law predicts 500 concurrent requests. This uses an assumed mean, not the p95 target as measured evidence. At 1 KB logical mutation payload, peak application writes are 2 MB/s before protocol, replication, indexes, and log overhead. Reads at 20,000/s with an assumed 90% cache hit rate leave 2,000/s view-store reads; cold-cache tests must cover far more. The final-item hotspot is a serial correctness problem, even when bandwidth is ample.

API, schema, and invariant

POST /v1/reservations
Idempotency-Key: buyer-request-uuid
{ sku, quantity: 1, ttl_seconds: 300 }
→ 201 { reservation_id, state: "held", expires_at, version }
POST /v1/reservations/{id}/confirm → confirmed | expired
DELETE /v1/reservations/{id} → released
GET /v1/items/{sku}/availability → { approximate_available, as_of }

inventory(sku PRIMARY KEY, available CHECK(available >= 0), version)
reservations(id PRIMARY KEY, sku, quantity, state, expires_at,
             buyer_id, version)
requests(buyer_id, key, request_hash, response, UNIQUE(buyer_id,key))
outbox(event_id PRIMARY KEY, reservation_id, version, type)

The invariant is available ≥ 0, with each held or confirmed unit accounted for exactly once. Under the authoritative transactional database, execute UPDATE inventory SET available=available-:q, version=version+1 WHERE sku=:sku AND available>=:q, require one affected row, then insert reservation, request response, and event in the same transaction. A check constraint is defense in depth; the conditional update decides acceptance. The database's selected transaction and consensus implementation must preserve this atomicity across failover.

Labeled architecture and progression

Region A clients → router ─┐
Region B clients → router ─┼→ current partition leader / authority
Region C clients → router ─┘          ↓ ordered transaction log
                            A replica ↔ B replica ↔ C replica
                            majority durable commit → acknowledge
                                     ↓ change events
                              regional read views/cache
CONTROL: consensus election + term/epoch → stale leader fenced

Begin with one authoritative write region and local replicas, then identify the unmet disaster objective: local-only durability does not provide RPO 0 for regional loss. Select a proven database offering the required cross-region synchronous durability and transactional behavior, and verify its documented failure modes. Do not implement consensus in application code. With three voting replicas placed in three independent regions, a majority can survive loss of one region if the remaining two communicate; placement, durable acknowledgment, and election configuration must be validated.

Partition inventory by sku so independent products scale. Each partition has one current logical authority. Consensus terms or epochs distinguish leadership generations; replicas reject operations from stale leaders. Application routing follows the elected authority and never promotes a disconnected copy simply because it is reachable. Consensus coordinates ordered state across replicas; replication alone does not imply safe ownership changes.

Three failure traces

  1. Region A loses connectivity: if B and C form a majority, they elect an authorized leader and resume writes after election. A cannot commit alone and rejects or times out writes. Local stale reads may continue only under the approved display contract. Checkout routes to the majority.
  2. Commit acknowledgment is lost: the buyer retries the original request key. The durable request record returns the same reservation. Do not decrement inventory again. If outcome cannot yet be established, report pending/retryable status rather than claiming failure and issuing a new operation.
  3. Hold expiry races confirmation: both transactions condition on current held state and database-evaluated expiry. Exactly one transition wins. Expiry restores quantity only if it changes held to expired; confirmation succeeds only before the deadline and changes held to confirmed. Duplicate expiry cannot increment stock twice.

Challenge and defended choice

Interviewer: “I need 50 ms writes everywhere, even during disconnection.” Candidate: “That conflicts with the 80 ms coordination path and our single shared-stock contract. We can change the contract by allocating regional quotas. A region sells only its locally owned quota, and transferring quota requires coordination. That buys local acceptance while some regions may show sold out despite remote stock.” This is escrow allocation: distribute bounded rights whose total never exceeds global inventory.

Reject unconstrained active-active counters merged after the fact: two regions may each sell the final unit, and conflict resolution cannot undo a physical promise. Reject asynchronous failover when claiming RPO 0; acknowledged data may not have reached the promoted region. Escrow is a legitimate alternative when quota fragmentation is acceptable, not a universal substitute for transactions. Allocation preserves the stock-rights bound, but does not independently provide RPO 0: reservations accepted only inside an isolated region can disappear if that region is then lost. Zero-loss acknowledgment still needs durable copies outside the regional failure domain, adding coordination latency or forcing rejection during isolation. If local-only isolated acceptance is required, explicitly renegotiate the durability/RPO contract rather than retaining the original promise.

Operations and evolution

Monitor quorum health, leader changes, replication/commit latency, rejected minority writes, reservation conflict rate, hold-expiry lag, and read-view age. Alert on user-visible symptoms and budget burn, not every election. Run regional isolation and recovery exercises, measure routing and retry convergence, and verify acknowledged reservations after failover. RTO includes detection, election, routing, and safe client recovery, not merely starting a replacement process.

Keep backups and point-in-time recovery for accidental deletion; quorum replicates mistakes too. Roll out schema changes compatibly across versions. Reconcile inventory movements with durable reservation events and investigate invariant violations rather than silently resetting counts. Add regional quota allocation only for appropriate product classes; high-demand scarce items may retain coordinated writes. Measure the cost of extra copies, cross-region traffic, and write latency against the business value of the stated disaster objective.

Follow-ups and rubric

Practice: the read cache says one item remains, but reservation fails. Is the design broken?

No. The displayed number is approximate. The authoritative conditional transaction decides, returns a clear conflict, and prompts a refresh. Misrepresenting the display as guaranteed would be a product contract error.

Practice: why does three replicas not automatically prove RPO 0?

All copies might share a failure domain, acknowledgment might precede durable replication, or failover might promote an incomplete replica. Verify placement, commit rules, failure scope, and safe promotion semantics.

Strong: states the partition behavior, enforces stock atomically, computes the latency lower bound and budget, and distinguishes recovery objectives from evidence. Weak: promises low latency, universal availability, and strict shared-stock correctness simultaneously. Principal depth includes quota alternatives, rollout compatibility, and tested recovery ownership.
