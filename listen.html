    Start here a sequence you can follow . A 45 minute interview method.

    A 45 minute interview method.

    0–5 minutes: restate the user action, define scope, ask for peak load, durability and freshness. Name one invariant: a condition that must always hold.

    5–10: estimate requests per second, bytes per day and concurrent work. Keep units. Decide which number actually changes the design.

    10–15: define two APIs, the source of truth and keys. Trace a successful write and read.

    15–25: draw a minimal working system. Label synchronous calls, durable writes and asynchronous edges. Explain the acknowledgment boundary.

    25–35: choose two deep dives driven by the prompt. Trace a retry after an ambiguous timeout and a dependency failure.

    35–42: evaluate skew, recovery, privacy, cost and growth. Explain one rejected alternative.

    42–45: summarize assumptions, the largest remaining risk and the experiment that would validate it.

    If the interviewer changes the scale, revise the bottleneck and retain unaffected decisions. Do not restart by naming fashionable components. Ask permission to spend time on correctness when the prompt involves money or inventory.

    1. Turn an ambiguous prompt into a contract . Start with a person and a decision.

    Start with a person and a decision.

    Corner Market is a fictional service connecting residents with local grocers. A shopper browses produce, reserves stock, pays, and collects an order. The examples are teaching assumptions, never claims about a real business. A system is the cooperating software, data, people, and operating procedures that deliver that journey. System design means choosing their boundaries and behavior under constraints. Before drawing boxes, say what success means for a shopper and what must never happen.

    A functional requirement describes behavior: reserve three apples for ten minutes. A nonfunctional requirement describes a quality of that behavior: finish most reservations quickly despite a failed server. An invariant is a rule that every valid state preserves: available stock never becomes negative. Availability is whether a request receives a useful response; durability is whether acknowledged data survives failures. These words answer different questions. A fast error is available only if the contract counts that error as useful.

    1. Turn an ambiguous prompt into a contract . Clarify the contract.

    Clarify the contract.

    Ask who uses the system, the three essential journeys, scope exclusions, traffic shape, data retention, geographic footprint, acceptable staleness, and failure expectations. Offer concrete choices. “Can a catalog show yesterday's price?” is better than “Do we need consistency?” Assume one city initially, catalog prices stale for at most sixty seconds, stock checked when reserving, and payment settlement handled by an external provider. Exclude delivery routing and tax calculation from the first interview. Record these assumptions visibly so an interviewer can change them.

    Separate a business promise from an implementation guess. “One successful payment capture per order” is a promise. “Use a distributed lock” is a candidate mechanism whose failure behavior needs proof. Ask what happens when a customer presses Pay twice, loses connectivity, or returns after a reservation expires. Those scenarios expose requirements that a component list misses. Include an explicit owner for every authoritative fact: inventory owns quantity; orders own checkout state; the payment provider reports money movement.

    1. Turn an ambiguous prompt into a contract . Before distributing: one machine can already race.

    Before distributing: one machine can already race.

    A process is a running program with its own memory space. Threads share a process's memory; separate processes generally do not share ordinary Python objects. An event loop runs tasks cooperatively: an awaiting task yields so another can run. Concurrency means operations overlap in time; parallelism means operations execute simultaneously. Two tasks can race even on one thread if a read and later write are separated by an await. Two servers each have their own local lock, so neither lock protects the other server's stock update.

    Trace one request: accept a socket, authenticate, acquire a bounded database connection, begin a transaction, conditionally change stock, commit, release the connection, respond. A connection pool reuses a limited set of database connections; it is not extra database capacity. If every request opens a new connection during a burst, setup and connection limits can fail before useful work starts. Bound waiting, keep transactions short, and let the database protect shared stock. The invariant stays the same when the application grows from one process to many.

    Estimate to change a decision.

    Capacity estimation is a simplified model of resources needed to serve a workload. It is useful when it chooses between designs or reveals an impossible promise. Corner Market has 100,000 daily active shoppers, each opening twenty catalog pages and placing 0.2 orders per day. These are explicit fictional baseline assumptions used throughout this foundation sequence. A day contains 86,400 seconds. Assume a tenfold peak-to-average factor for requests, a 2 kilobytes decimal catalog response excluding photos, a 1 kilobytes order record before indexes, and thirty-day hot order retention.

    Catalog traffic is 100,000 times 20 equals 2,000,000 requests per day. Dividing by 86,400 gives approximately 23.15 requests per second on average and 231.5 at the assumed peak. Orders are 100,000 times 0.2 equals 20,000 per day, approximately 0.2315 per second average and 2.315 per second peak. Do not say “millions of users require sharding”: this baseline may fit a modest database. Search, photos, expensive joins, geographic distance, and bursts may matter more than total user count.

    Keep units attached.

    Two million catalog responses times 2,000 bytes equals 4,000,000,000 bytes per day, or 4 gigabytes using decimal units.     2. Estimate load with units and uncertainty . Concurrency and service time.

    Concurrency and service time.

    Concurrency is work in progress. For a stable system, average work in progress equals arrival rate times average time in the system; this is Little's Law. At 231.5 requests per second and 0.2 seconds average response time, approximately 46.3 requests are in flight. This does not mean forty-seven C P U cores are required: much of the time may be waiting for a database or network. If each request actually consumes 5 milliseconds of C P U time, that workload consumes 1.1575 C P U-seconds per second before overhead, suggesting more than one fully utilized core and headroom for bursts.

    Utilization is the fraction of resource capacity in use. Queueing delays rise sharply as arrivals approach service capacity, so a benchmark at maximum throughput is not a safe operating target. Measure throughput together with tail latency: 99th percentile is the response time below which ninety-nine percent of observations fall. Percentiles do not add across services. A whole-request 99th percentile cannot be obtained by simply adding each dependency's 99th percentile because their slow events may overlap or occur on different requests.

    Model the awkward workload.

    A flash sale can invalidate the tenfold assumption. Suppose 5,000 shoppers attempt to reserve the same item within one second. Total catalog load remains unremarkable, but one inventory row receives 5,000 contending writes. A hot key is one identifier receiving disproportionate traffic. More database shards do not divide one indivisible stock counter. Consider admission control, a waiting room, partitioned stock allocations with reconciliation, or accepting fewer requests while preserving the invariant. Select the mechanism only after discussing acceptable customer behavior.

    Use sensitivity analysis: recompute the result when an uncertain input changes. At 200 kilobytes per page instead of 2 kilobytes, catalog transfer becomes 400 gigabytes per day. At a hundredfold peak rather than tenfold, peak request rate becomes 2,315 per second. Write low, expected, and high assumptions; identify which measurement you would collect first. Load tests should reproduce skew, cold caches, slow dependencies, and retry storms, not just uniform random successful reads.

    Practice: a worker drains 150 jobs per second while 250 arrive each second for two minutes. What backlog forms?.

    The deficit is 100 jobs per second, so 12,000 jobs accumulate after 120 seconds, assuming zero initial backlog and constant rates. When arrivals fall to 50 per second, net drainage is 100 per second, requiring another 120 seconds. “Autoscale workers” is incomplete unless the downstream database can absorb their added load.

    Exit artifact: a worksheet with assumptions, equations, units, peak factors, uncertainty ranges, and the architectural decision each estimate informs. Recalculate without a calculator first, then verify arithmetic; order-of-magnitude mistakes should become visible before precision distracts you.

    3. Follow a request and design a durable A P I . Trace the path.

    Trace the path.

    A network request crosses independently failing boundaries. The shopper's client resolves a hostname using the DNS, establishes a transport connection, negotiates TLS, and sends an H T T P request. A load balancer distributes requests among healthy application instances. Connection reuse avoids repeating setup for every request, but a broken reused connection still needs bounded recovery. A server marked healthy may have a failing database, so distinguish process liveness from readiness to accept useful traffic.

    Latency is elapsed time for one operation; throughput is completed operations per unit time. Greater bandwidth does not remove a long round trip. Four sequential dependent calls across a 70-millisecond path spend at least 280 milliseconds on those trips before processing. Batch independent lookups, colocate related operations, or redesign a chatty interface. Parallel calls help independent work but create additional load and complicate cancellation when the parent request no longer needs results.

    3. Follow a request and design a durable A P I . A reservation contract.

    A reservation contract.

    Expose POST /v1/reservations with a client-generated Idempotency-Key, authenticated shopper identity, store identifier, item identifier, quantity, and expected price version. An idempotent effect means repeating an operation does not multiply its intended state change. This endpoint implements that property through a stored key scoped to the shopper and operation; merely naming a header does not provide it. Save a hash of the request body so reuse with different content is rejected.

    The example creates a reservation at the version-one reservation endpoint. The shopper sends a stable idempotency key, identifies store s seven and the apple item, requests three units, and supplies observed price version twelve. The service checks authenticated ownership and authoritative stock and price rules. A successful created response identifies reservation r eighty-one, marks it held, and includes expiration and version one. If the response is lost, the client repeats the same logical request under the same key or retrieves its result. Generating a new key would identify another operation and could create another hold.

    The schema is deliberately small. Quantity must be a positive bounded integer. Price is checked against a server-owned version. The response contains a stable identifier that GET /v1/reservations/r81 can retrieve after a timeout. The key table stores shopper, operation, key, body hash, result identifier, and expiration. Commit the key and reservation together. Retain keys for the documented retry window; clients cannot assume protection after keys expire.

    3. Follow a request and design a durable A P I . Errors are part of the interface.

    Errors are part of the interface.

    Return a structured error with a machine-readable code, human-readable message, request identifier, and retry guidance. Distinguish invalid quantity, unavailable stock, authorization failure, and temporary dependency failure. H T T P defines method and status semantics; for example, GET is safe, and PUT and DELETE have idempotent semantics, while POST is not inherently idempotent. Those properties concern intended server effects, not whether every repeated response has identical bytes. See RFC 9110, checked 2026-10-19.

    A timeout tells the client it stopped waiting; it does not prove the server failed. Set a total request deadline and allocate smaller dependency timeouts within it. If a 500-millisecond server deadline allows a database call to wait two seconds, the work outlives its purpose. Propagate cancellation where supported, but preserve a committed operation's retrievable outcome. Retry only operations whose effects are safe to repeat, with a limited attempt count, increasing delay, and randomness to avoid synchronized retries.

    Pagination, compatibility, and trust.

    For order history, sort by (created_at, order_id) and return an opaque cursor containing the last pair. Keyset pagination resumes from the last observed key; offset pagination skips a count of rows and can become expensive or unstable when new rows arrive. Define whether a browsing session sees a fixed snapshot or a changing history. Always add a unique tiebreaker because timestamps can coincide.

    Authentication establishes identity; authorization decides whether that identity may perform this operation on this object. Never accept a supplied shopper identifier as proof of ownership. Enforce authorization on each retrieved reservation and each mutation. Bound body sizes, item counts, and query complexity. Avoid putting secrets in URLs because URLs often enter logs.     The server may interpret the retry as a second operation and hold stock twice. Retry with the same key and unchanged body, or retrieve the original result. If the original key is unknown because local client state was lost, show pending status and reconcile rather than claiming the first attempt failed.

    4. Model data around queries and invariants . Choose the unit of truth.

    Choose the unit of truth.

    A data model defines records, relationships, valid states, and access patterns. Corner Market begins with stores, items, inventory, reservations, orders, and payment attempts. A primary key uniquely identifies a record; a foreign key constrains a reference to another record. Inventory belongs to a store-item pair. Reservations record quantity and expiration, while order lines preserve the purchased description and price. Copying the purchased price is intentional history: a later catalog edit must not rewrite an old receipt.

    Inventory is uniquely identified by store and item, with available quantity constrained to remain nonnegative and a version supporting concurrency control. Reservations record shopper ownership, quantity, state, and expiry. Order headers keep shopper, state, and creation time, while order lines preserve item quantity, historical unit price in minor units, and currency. Historical order prices must not change when a catalog price changes. Request keys are uniquely scoped by shopper, operation, and key. Their body hash detects reuse for different content, and their result identifier retrieves the original effect. These relationships define authority and retry behavior before any cache is introduced.

    Money uses an integer in the currency's defined minor unit or a carefully selected decimal representation, with currency stored explicitly. Do not assume every currency has two decimal places. State transitions are explicit: held becomes confirmed or expired; confirmed does not silently become held again. A separate adjustment records a refund. The database is authoritative; a search index and cache are derived views that can be rebuilt.

    4. Model data around queries and invariants . Atomicity beats a hopeful read.

    Atomicity beats a hopeful read.

    A transaction groups operations that succeed or fail together. Atomicity means no partial committed result; isolation controls interference among concurrent transactions. For one stock row, use a conditional update and check the affected-row count, then insert the reservation in the same transaction:.

    Begin one database transaction. Conditionally decrement the apple inventory at store s seven by three, while incrementing its version, only if at least three units remain. Continue only when exactly one row changed. Then insert the reservation and commit the complete unit. If stock was insufficient, do not insert a successful hold. If insertion fails, roll back the decrement. The important concurrency property is that the stock check and decrement occur inside one database update, rather than a separate application read followed by a stale write. Commit joins the accepted hold and its inventory effect.

    Reading available stock into application memory, checking it, and later writing a new value can lose concurrent changes. The conditional update makes the eligibility check and decrement one database operation. A database constraint supplies a final guard. Multi-item orders need one transaction with consistent lock order, or an explicit partial-reservation workflow and compensation. A deadlock is a cycle of transactions waiting on each other's locks; retry the aborted transaction with a bounded policy.

    4. Model data around queries and invariants . Isolation is a choice with consequences.

    Isolation is a choice with consequences.

    Serializable isolation makes committed concurrent transactions behave like some serial ordering. It may abort work that must then be retried. PostgreSQL's default Read Committed isolation gives each statement its own committed snapshot; Repeatable Read provides a stable transaction snapshot but does not eliminate every serialization anomaly. Consult PostgreSQL transaction isolation, checked 2026-10-19. These product-specific facts do not imply every database implements identically named levels the same way.

    Consider an invariant across two rows: at least one on-call stock reconciliation worker must remain active. Two transactions can each observe two active workers and disable a different worker, leaving none. This is write skew: independent writes violate a shared predicate. Protect the actual invariant using a locked coordinating row, a serializable transaction with retries, or a model that makes the decision atomic. Choosing “a transaction” without identifying its isolation and locked data is insufficient.

    4. Model data around queries and invariants . Indexes buy reads with writes and space.

    Indexes buy reads with writes and space.

    An index is an auxiliary structure locating records without scanning every row. For WHERE shopper_id equals ? ORDER BY created_at DESC, id DESC LIMIT 20, consider an index on (shopper_id, created_at DESC, id DESC). Composite-index order should follow actual predicates and sort requirements. PostgreSQL documents how leading equality constraints affect multicolumn B-tree scans in Multicolumn Indexes, checked 2026-10-19. Verify with realistic query plans and data distributions; adding every imaginable index increases write work and storage.

    A relational store suits the first design because relationships and atomic updates dominate. Object storage suits large immutable product images; storing image bytes in order rows bloats transactional reads and backups. A document store may suit independently retrieved product documents, but denormalizing inventory into every document creates a synchronization problem. Choose based on operations and invariants rather than declaring one category universally faster.

    Practice: how does reservation expiry avoid returning stock twice?.

    Within a transaction, change held to expired only when its state is still held and the deadline has passed. Return quantity only if that transition changed a row. Repeated expiry attempts then do nothing. Confirm and expire must contend over the same reservation state so only one transition wins. Test a race between those operations.

    Exit artifact: write three important queries, propose their indexes, and state which invariant each transaction protects. Explain recovery when the process crashes before commit and after commit but before responding.

    Lost update: stock starts at five. A reads five; B reads five; A computes four and writes four; B computes four and writes four. Two reservations were accepted but only one unit was deducted. The invariant “at least one active worker” fails. Serialize the decision using one coordinating row or use serializable isolation with whole-transaction retries.

    5. Cache with a freshness and failure contract . A cache is a disposable copy.

    A cache is a disposable copy.

    A cache stores data closer to its consumer or in a faster medium to reduce latency or repeated computation. It creates another version of reality. Corner Market can cache product descriptions because a short delay is tolerable; the final stock reservation still consults authoritative inventory. First define the maximum acceptable staleness, key ownership, invalidation mechanism, eviction behavior, and what happens when the cache disappears. A cache that is necessary to reconstruct purchases is functioning as a database and needs a different durability contract.

    In cache-aside, the application checks a key, reads the database on a miss, and populates the cache. A hit returns the cached value. A T T L bounds an entry's residence time, not necessarily the age of the underlying fact if a stale source repopulates it. Use versioned product values and include the version in invalidation messages. Keep shopper-private results out of shared public keys; include tenant, authorization scope, language, and other response-shaping inputs where appropriate.

    The database-to-broker gap.

    If an order commits and then the process crashes before publishing its event, downstream systems never hear about the order. Publishing first has the opposite problem: consumers may see an order that later rolls back. The transactional outbox writes the order and an event row in the same database transaction. Include event identifier, entity identifier, schema version, occurrence time, and necessary nonsecret data. Avoid copying every personal field into every event. Retention, access control, and deletion become harder as copies multiply. A schema change should tolerate older consumers during rollout.
