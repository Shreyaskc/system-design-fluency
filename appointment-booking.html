LESSON 24 / 27 · ORIGINAL TEACHING EXAMPLES

Case 11 · Book a community pickup appointment

Corner Market partners with community clinics to schedule equipment pickups and service appointments. An available calendar cell is a hint; a confirmed booking is a promise enforced by a transaction.

Exact interview prompt

Design appointment booking across 2,000 community clinics. Users browse available slots, book one, cancel, and retry after network failures. Prevent double booking and explain how your design evolves.

Clarification dialogue and requirements

Interviewer: “Can users choose arbitrary durations?” Candidate: “May I begin with fixed, pre-generated, single-capacity slots? Overlapping variable-duration appointments require interval conflict detection.” Interviewer: “Yes. Confirmations must never overlap for a slot.” Candidate: “Then the booking transaction, not the cached calendar, owns that invariant.”

Assume each clinic offers 100 slots/day, published 90 days ahead. One account can book multiple distinct slots, subject to abuse limits. Cancellation releases capacity; no payment or temporary holds in the first version. Ask about rescheduling: support an atomic move within the same database. Store instants in UTC with the clinic's named time zone for display and schedule generation. A local time can be ambiguous or nonexistent around daylight-saving changes; generate slots using an explicit policy and preserve the resulting instant. The examples are fictional assumptions.

Propose 99.9% monthly booking availability and p95 server response below 300 ms under normal regional operation. Successful confirmation means a durable transaction committed. Availability browsing may lag by five seconds; booking always checks current authoritative state. Users receive a conflict response when another person wins. Notifications are asynchronous and do not determine whether the appointment exists.

Work the numbers

2,000 clinics × 100 slots/day × 90 days = 18 million slot rows. At 200 logical bytes/row, that is 3.6 GB before indexes, row overhead, booking history, replicas, and backups. Three full copies of those logical bytes alone total 10.8 GB. Assume 200 peak mutations/s and a measured or hypothesized 50 ms mean database residence time. Little's law gives average in-flight database work L = arrival rate × residence time = 200/s × 0.05 s = 10 concurrent operations. This is not a recommendation for a ten-connection pool: transaction contention, headroom, failover, and tail latency still require measurement.

Assume 20 browse requests per mutation: 4,000 peak browse requests/s. Cache clinic-day availability for up to five seconds, coalesce concurrent misses, and bound fallback concurrency. A single famous clinic can still create a hot slot even when aggregate database load is small; its successful write capacity is one booking, regardless of infrastructure size.

API, schema, and exact enforcement

GET /v1/clinics/{id}/slots?date=2026-11-03
POST /v1/bookings
Idempotency-Key: client-request-uuid
{ slot_id: "s42" }
→ 201 { booking_id, slot_id, state: "confirmed" }
DELETE /v1/bookings/{id} → 204
POST /v1/bookings/{id}/reschedule { new_slot_id }

slots(id PRIMARY KEY, clinic_id, starts_at, ends_at,
      active_booking_id NULL, version,
      UNIQUE(clinic_id, starts_at), CHECK(ends_at > starts_at))
bookings(id PRIMARY KEY, slot_id, user_id, state, created_at)
requests(user_id, key, request_hash, response,
         UNIQUE(user_id, key))
outbox(event_id PRIMARY KEY, booking_id, event_type)

Enforce one active occupant with an atomic conditional update: UPDATE slots SET active_booking_id=:booking WHERE id=:slot AND active_booking_id IS NULL. Require exactly one affected row, then insert booking, request response, and notification outbox row in the same transaction. Roll back all work on failure. The slot primary key makes all competing updates contend on the same authoritative row. An idempotency key identifies one intended action across retries; a repeated key with different input is rejected. Serialize concurrent uses of the same key using its unique request record inside the transaction.

Labeled architecture and progression

BROWSE: client → calendar API → clinic-day cache → slot database
BOOK:   client → authenticated booking API → database transaction
                                  [slot + booking + request + outbox]
                                                          ↓ dispatcher
                                                 notification worker
INVALIDATE: committed change → cache invalidation (TTL is fallback)

Start with a relational database, stateless API, and no cache until browsing warrants it. Cancellation locks the booking and clears the slot only when active_booking_id matches that booking, then updates state and writes an outbox event in one transaction. This comparison prevents a delayed duplicate cancellation from clearing a later occupant's booking. Repeated cancellation returns the existing cancelled outcome.

Rescheduling first locks and re-reads the booking row and verifies it remains confirmed and owned by the caller, using the same booking-then-slot lock order as cancellation. It then locks old and new slot rows in a consistent ID order to reduce deadlocks, verifies the old slot still points to this booking and the new slot is available, releases old capacity, claims new capacity, and updates the booking atomically. On conflict, preserve the old appointment. Retry deadlock victims with the same idempotency key and bounded backoff. A transaction boundary matters more here than introducing a queue.

Three failure traces

  1. Two users book s42: A updates the empty slot and commits. B waits on the row, then its conditional predicate no longer matches. B changes zero rows and receives 409. A stale browse cache cannot override this result.
  2. Commit succeeds; response disappears: the client retries the same key. The stored response returns the original booking. A new key would mean a new intended operation and must not be substituted automatically.
  3. Notification worker crashes after sending: outbox replay may send a duplicate notification. The booking remains confirmed once. Include a stable event ID and use provider deduplication when supported; otherwise notifications remain at least once.

Challenge, alternatives, and operations

Interviewer: “Why not lock the slot in Redis?” Candidate: “A cache lock expiring during a slow database operation can permit two holders. The database conditional update already enforces the invariant where durable state lives. I would use a distributed lock only with a demonstrated need and a fencing mechanism enforced by the resource.” A fencing mechanism rejects stale owners using increasing ownership versions.

Reject read-then-write availability checks without atomic enforcement. Reject serializing every clinic through one global queue because independent slots need no shared order. If variable durations arrive, fixed slot uniqueness is insufficient: use interval reservations with an exclusion constraint or serialize each resource's overlap check and insertion under an appropriate transaction policy. Do not assume a row-level check constraint can enforce arbitrary cross-row non-overlap.

Monitor booking latency, conflict rate, lock wait time, deadlocks, request-key conflicts, outbox lag, and cache age. A high conflict rate may reflect real scarcity rather than a broken service. Protect popular releases with admission control and per-account limits. Audit staff overrides and cancellation ownership. Restore drills must verify slot pointers and booking state together.

Evolve temporary holds only with an explicit expiry authority: a hold consumes capacity until a database-checked deadline; a late confirmation must atomically verify that hold still owns the slot. Partition by clinic when measured pressure warrants it. Cross-partition rescheduling then requires a different product contract or coordination; explain that added complexity before promising the original atomic behavior.

Follow-ups and rubric

Practice: cancellation retries after another user has booked the released slot. What prevents damage?

Clear only if the slot still points to the cancelled booking. The old request must not unconditionally clear active_booking_id.

Practice: does five-second calendar caching allow five seconds of double booking?

No. Caching affects displayed availability only. Every confirmation uses the authoritative conditional transaction.

Strong: identifies the slot invariant, names the atomic enforcement, handles ambiguous responses, and preserves the old booking on failed reschedule. Weak: equates a cached “available” flag with a reservation or proposes locks without expiry/failure semantics. Principal depth includes interval evolution and cross-partition contract changes.
