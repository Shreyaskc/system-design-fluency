LESSON 01 / 27 · ORIGINAL TEACHING EXAMPLES

Start here · a sequence you can follow

This course follows Corner Market, a fictional neighborhood marketplace. Begin with one request and one database. Add a distributed component only after identifying the failure or capacity limit it addresses. All traffic figures are teaching assumptions, not facts about any company.

Start here: three paths through one sequence

PathSequence and proof of learning
New to design · 8 weeksWeeks 1–2: requirements, estimates, APIs, concurrency and storage. Weeks 3–4: caching through messaging. Week 5: reliability and multi-region. Weeks 6–8: two cases per week, then a timed redesign. Spend 5–7 hours per week; repeat a week when the exit task fails.
Experienced builder · 4 weeksRun the labs and explain every failed invariant first. Study the missed foundations. Solve URL shortener, reservations and streaming; then choose two unfamiliar cases. Write an operational rollback plan for each.
Principal preparation · 2 week diagnostic sprintReview constraints, correctness, reliability and evolution. Solve three unseen cases with a partner. Require explicit ownership, migration, cost model and failure containment. This is a diagnostic, not a shortcut to principal experience.

Prerequisites and exit criteria

You should be able to read a Python function, explain a dictionary lookup, write a SQL SELECT, and distinguish a byte from a bit. A byte is eight bits; 1 MB here means 1,000,000 bytes, so a 10 MB/s payload is 80 Mb/s before protocol overhead. A SQL query such as SELECT n FROM stock WHERE id=1 reads the column n from the matching row. A Python dictionary maps keys to values; its lookup is expected constant time under ordinary hash assumptions. If Python functions or basic SQL are new, learn those prerequisites first; the labs below are application exercises rather than a complete programming introduction. Run python3 labs/design.py and manually trace its assertions once those basics are comfortable. No cloud account or package installation is needed.

High-level design (HLD) assigns responsibilities to services and stores and explains data movement, capacity and failure behavior. Low-level design (LLD) specifies interfaces, state transitions and concurrency within a component. A box marked “payment service” is HLD; the permitted transition from pending to captured and its idempotency key are LLD. A convincing answer connects both.

A 45 minute interview method

  1. 0–5 minutes: restate the user action, define scope, ask for peak load, durability and freshness. Name one invariant: a condition that must always hold.
  2. 5–10: estimate requests per second, bytes per day and concurrent work. Keep units. Decide which number actually changes the design.
  3. 10–15: define two APIs, the source of truth and keys. Trace a successful write and read.
  4. 15–25: draw a minimal working system. Label synchronous calls, durable writes and asynchronous edges. Explain the acknowledgment boundary.
  5. 25–35: choose two deep dives driven by the prompt. Trace a retry after an ambiguous timeout and a dependency failure.
  6. 35–42: evaluate skew, recovery, privacy, cost and growth. Explain one rejected alternative.
  7. 42–45: summarize assumptions, the largest remaining risk and the experiment that would validate it.

If the interviewer changes the scale, revise the bottleneck and retain unaffected decisions. Do not restart by naming fashionable components. Ask permission to spend time on correctness when the prompt involves money or inventory.

How to use each lesson

Read the request trace, then cover the solution and reproduce it. Change one assumption: tenfold load, a slow replica, a duplicate message, or a regional partition. Explain which guarantee changes and why. Answer disclosures remain closed until you open them. Diagrams are plain text with labeled edges so they remain selectable, zoomable and usable without a graphics library.

First diagnostic: the checkout timed out. Should the client retry?

The timeout does not prove failure. The server may have committed the order before its response was lost. Retry the same logical operation with a stable idempotency key and query its durable result. A new key can create a second order. A blanket “never retry writes” also fails availability goals.

Evidence of mastery

The study checkbox records reading in your browser only. It is not a score. Re-solve after 48 hours without notes. A correct answer you cannot defend under changed assumptions is recognition, not mastery.
