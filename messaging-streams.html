8. Make asynchronous work replayable and bounded

Listen to this chapter →

Separate accepting work from finishing it

Asynchronous processing records work for another process to finish later. Corner Market should not fail a committed order because email is temporarily unavailable. A queue distributes tasks to workers; a log retains an ordered sequence that consumers can read independently. Choose a task queue for sending receipts and a retained event log when analytics, search indexing, and audit projections need independent replay. “Asynchronous” does not mean instantaneous, durable, or guaranteed to succeed.

The response must distinguish accepted from completed. Return a stable job identifier and state such as pending, running, succeeded, or failed. Define the maximum queueing delay and how users learn about terminal failure. A worker acknowledgment tells the broker the worker has completed its obligation; acknowledge too early and a crash loses work, acknowledge too late and successful work may be repeated. Exactly which effect counts as completion needs an explicit contract.

The database-to-broker gap

If an order commits and then the process crashes before publishing its event, downstream systems never hear about the order. Publishing first has the opposite problem: consumers may see an order that later rolls back. The transactional outbox writes the order and an event row in the same database transaction. A relay publishes committed event rows and marks progress. Relay crashes can duplicate publication, so consumers must tolerate repeated event identifiers.

BEGIN;
INSERT INTO order_header (...);
INSERT INTO outbox (event_id, aggregate_id, kind, payload) VALUES (...);
COMMIT;
-- relay publishes only committed outbox records

An event is a statement about something that occurred, such as OrderConfirmed; a command requests an action, such as SendReceipt. Include event identifier, entity identifier, schema version, occurrence time, and necessary nonsecret data. Avoid copying every personal field into every event. Retention, access control, and deletion become harder as copies multiply. A schema change should tolerate older consumers during rollout.

Delivery and effects

At-least-once delivery may repeat a message; at-most-once delivery may lose it. Exactly-once claims always need a boundary. Apache Kafka documents transactional processing guarantees and the limits when interacting with external systems in its design documentation, checked 2026-10-19. A broker transaction does not automatically make an external email or payment provider participate atomically.

For a local projection, insert the event identifier into a processed-events table and update the projection in one database transaction under a unique constraint. For an external effect, pass a stable provider idempotency key if the provider supports a suitable contract, or maintain an attempt record and reconcile uncertain outcomes. A worker that crashes after sending a receipt but before recording completion can send it twice on retry; accepting duplicate email may be reasonable, accepting duplicate captures is not.

Ordering and event time

A partition is an independently ordered subset of a log. Key inventory events by store-item when per-item ordering matters. There is no global order across independent partitions unless an additional mechanism creates one. Consumers must handle missing versions and out-of-order arrivals from other sources. An event's occurrence time differs from processing time. A receipt event generated offline may arrive after newer events, so a dashboard must state its policy for late data.

A watermark estimates event-time completeness for a processing window; it is a policy based on observed progress and lateness assumptions, not proof that no older event can ever arrive. Count orders in five-minute windows with a defined late-arrival allowance, then emit corrections or route very late events for reconciliation. Distinguish business totals from an approximate live chart so an operational dashboard does not become an accidental financial ledger.

Backpressure and poison messages

Backpressure slows or rejects producers when consumers cannot keep up. At 250 arrivals/second and 150 completions/second, backlog grows by 100/second. A large queue postpones overload; it does not create capacity. Bound queue size, prioritize critical work, limit worker concurrency, and protect downstream services. Track oldest-message age alongside queue depth because users experience delay, not abstract message counts.

A poison message repeatedly fails due to data or code that retries cannot fix. Retry transient failures with a bounded schedule, then isolate the item in a dead-letter queue with reason and safe inspection tools. Assign an owner and replay procedure. Replaying an entire backlog after a bug fix must preserve deduplication and downstream rate limits. Otherwise recovery becomes a second incident.

Practice: a consumer crashes after updating its projection but before acknowledging. What must happen on replay?

The projection update and processed-event record commit together. On replay the unique event identifier reveals prior completion, so the consumer acknowledges without repeating the update. If those writes are separate, a crash between them can still double-count or skip work.

Exit artifact: draw the crash points before and after each commit, publish, external call, and acknowledgment. For every point, state whether replay loses, duplicates, or safely repeats the intended effect.

Request trace: One projection effect per event

Order O commits with outbox event E; relay publishes E; consumer commits a count increment and E receipt together; acknowledgment is lost; E returns. The receipt prevents a second increment. Choose at-least-once transport with atomic deduplication for this projection because occasional retries are preferable to silently missing orders.
