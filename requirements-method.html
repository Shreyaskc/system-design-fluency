LESSON 02 / 27 · ORIGINAL TEACHING EXAMPLES

1. Turn an ambiguous prompt into a contract

Start with a person and a decision

Corner Market is a fictional service connecting residents with local grocers. A shopper browses produce, reserves stock, pays, and collects an order. The examples are teaching assumptions, never claims about a real business. A system is the cooperating software, data, people, and operating procedures that deliver that journey. System design means choosing their boundaries and behavior under constraints. Before drawing boxes, say what success means for a shopper and what must never happen.

A functional requirement describes behavior: reserve three apples for ten minutes. A nonfunctional requirement describes a quality of that behavior: finish most reservations quickly despite a failed server. An invariant is a rule that every valid state preserves: available stock never becomes negative. Availability is whether a request receives a useful response; durability is whether acknowledged data survives failures. These words answer different questions. A fast error is available only if the contract counts that error as useful.

Clarify the contract

Ask who uses the system, the three essential journeys, scope exclusions, traffic shape, data retention, geographic footprint, acceptable staleness, and failure expectations. Offer concrete choices. “Can a catalog show yesterday's price?” is better than “Do we need consistency?” Assume one city initially, catalog prices stale for at most sixty seconds, stock checked when reserving, and payment settlement handled by an external provider. Exclude delivery routing and tax calculation from the first interview. Record these assumptions visibly so an interviewer can change them.

Separate a business promise from an implementation guess. “One successful payment capture per order” is a promise. “Use a distributed lock” is a candidate mechanism whose failure behavior needs proof. Ask what happens when a customer presses Pay twice, loses connectivity, or returns after a reservation expires. Those scenarios expose requirements that a component list misses. Include an explicit owner for every authoritative fact: inventory owns quantity; orders own checkout state; the payment provider reports money movement.

Before distributing: one machine can already race

A process is a running program with its own memory space. Threads share a process's memory; separate processes generally do not share ordinary Python objects. An event loop runs tasks cooperatively: an awaiting task yields so another can run. Concurrency means operations overlap in time; parallelism means operations execute simultaneously. Two tasks can race even on one thread if a read and later write are separated by an await. Two servers each have their own local lock, so neither lock protects the other server's stock update.

Trace one request: accept a socket, authenticate, acquire a bounded database connection, begin a transaction, conditionally change stock, commit, release the connection, respond. A connection pool reuses a limited set of database connections; it is not extra database capacity. If every request opens a new connection during a burst, setup and connection limits can fail before useful work starts. Bound waiting, keep transactions short, and let the database protect shared stock. The invariant stays the same when the application grows from one process to many.

A forty-five-minute interview

Spend minutes zero through five defining journeys and invariants; five through ten estimating the dominant load; ten through twenty choosing APIs, records, and the simplest end-to-end design; twenty through thirty-five exploring the two highest-risk decisions; thirty-five through forty-two analyzing failures and evolution; and the final three minutes summarizing choices and unresolved risks. This is a negotiation aid, not a rigid performance script. Ask whether the interviewer prefers correctness, scale, or operations before selecting deep dives.

HLD explains why an order service talks to inventory and how failures cross that boundary. LLD explains the reservation state machine, repository interface, and concurrency-safe update. Move between levels when it resolves a risk. Writing twenty classes before deciding whether stock may oversell is premature; drawing services without explaining one atomic stock update is incomplete.

Build and challenge the smallest design

Begin with a web application and relational database. Follow one reserve request from authentication through validation, conditional inventory update, order creation, commit, and response. Then deliberately break a dependency: the response is lost after commit. The client cannot distinguish this from a failed commit, so introduce a stable request identifier and a retrievable result. Add a queue only when email should succeed independently from checkout; add a cache only when a measured read bottleneck or geographic latency calls for one.

A useful drawing labels arrows with operation and protocol, stores with ownership, and boundaries with failure scope. Write the invariant beside the transaction boundary. Every new component should answer three questions: what pressure requires it, what new failure does it create, and how will operators know that it works? A principal-level discussion also identifies the team that can operate the choice and a migration plan that avoids rewriting everything simultaneously.

Practice: the interviewer says “design a grocery app.” What do you say first?

“I will focus on browsing, reserving inventory, and checkout. Is one city sufficient? Must we prevent overselling, and can catalog data lag by sixty seconds? I assume one successful capture per order and external payment processing. I will first show a working single-region flow, then explore hot inventory and payment timeouts.” This makes scope and correctness reviewable. A weak answer immediately names five databases without establishing any promise.

Completion check: write a one-page contract for a library hold system using the same method, then explain which grocery assumptions no longer apply. Reading this chapter is study completion; doing that exercise with a changed prompt supplies evidence of transfer.
