4. Model data around queries and invariants

Choose the unit of truth

A data model defines records, relationships, valid states, and access patterns. Corner Market begins with stores, items, inventory, reservations, orders, and payment attempts. A primary key uniquely identifies a record; a foreign key constrains a reference to another record. Inventory belongs to a store-item pair. Reservations record quantity and expiration, while order lines preserve the purchased description and price. Copying the purchased price is intentional history: a later catalog edit must not rewrite an old receipt.

inventory(store_id, item_id, available, version)
  PRIMARY KEY(store_id, item_id), CHECK(available >= 0)
reservation(id, shopper_id, store_id, item_id, quantity, state, expires_at)
order_header(id, shopper_id, state, created_at)
order_line(order_id, item_id, quantity, unit_price_minor, currency)
request_key(shopper_id, operation, key, body_hash, result_id)
  UNIQUE(shopper_id, operation, key)

Money uses an integer in the currency's defined minor unit or a carefully selected decimal representation, with currency stored explicitly. Do not assume every currency has two decimal places. State transitions are explicit: held becomes confirmed or expired; confirmed does not silently become held again. A separate adjustment records a refund. The database is authoritative; a search index and cache are derived views that can be rebuilt.

Atomicity beats a hopeful read

A transaction groups operations that succeed or fail together. Atomicity means no partial committed result; isolation controls interference among concurrent transactions. For one stock row, use a conditional update and check the affected-row count, then insert the reservation in the same transaction:

BEGIN;
UPDATE inventory SET available = available - 3, version = version + 1
WHERE store_id = 's7' AND item_id = 'apple' AND available >= 3;
-- continue only if exactly one row changed
INSERT INTO reservation (...) VALUES (...);
COMMIT;

Reading available stock into application memory, checking it, and later writing a new value can lose concurrent changes. The conditional update makes the eligibility check and decrement one database operation. A database constraint supplies a final guard. Multi-item orders need one transaction with consistent lock order, or an explicit partial-reservation workflow and compensation. A deadlock is a cycle of transactions waiting on each other's locks; retry the aborted transaction with a bounded policy.

Isolation is a choice with consequences

Serializable isolation makes committed concurrent transactions behave like some serial ordering. It may abort work that must then be retried. PostgreSQL's default Read Committed isolation gives each statement its own committed snapshot; Repeatable Read provides a stable transaction snapshot but does not eliminate every serialization anomaly. Consult PostgreSQL transaction isolation, checked 2026-10-19. These product-specific facts do not imply every database implements identically named levels the same way.

Consider an invariant across two rows: at least one on-call stock reconciliation worker must remain active. Two transactions can each observe two active workers and disable a different worker, leaving none. This is write skew: independent writes violate a shared predicate. Protect the actual invariant using a locked coordinating row, a serializable transaction with retries, or a model that makes the decision atomic. Choosing “a transaction” without identifying its isolation and locked data is insufficient.

Indexes buy reads with writes and space

An index is an auxiliary structure locating records without scanning every row. For WHERE shopper_id = ? ORDER BY created_at DESC, id DESC LIMIT 20, consider an index on (shopper_id, created_at DESC, id DESC). Composite-index order should follow actual predicates and sort requirements. PostgreSQL documents how leading equality constraints affect multicolumn B-tree scans in Multicolumn Indexes, checked 2026-10-19. Verify with realistic query plans and data distributions; adding every imaginable index increases write work and storage.

A relational store suits the first design because relationships and atomic updates dominate. Object storage suits large immutable product images; storing image bytes in order rows bloats transactional reads and backups. A document store may suit independently retrieved product documents, but denormalizing inventory into every document creates a synchronization problem. Choose based on operations and invariants rather than declaring one category universally faster.

Practice: how does reservation expiry avoid returning stock twice?

Within a transaction, change held to expired only when its state is still held and the deadline has passed. Return quantity only if that transition changed a row. Repeated expiry attempts then do nothing. Confirm and expire must contend over the same reservation state so only one transition wins. Test a race between those operations.

Exit artifact: write three important queries, propose their indexes, and state which invariant each transaction protects. Explain recovery when the process crashes before commit and after commit but before responding.

Predict two interleavings

Lost update: stock starts at five. A reads five; B reads five; A computes four and writes four; B computes four and writes four. Two reservations were accepted but only one unit was deducted. The invariant is that decrements equal accepted quantities. A conditional database decrement, not application read-modify-write, fixes this single-row race.

Write skew: workers A and B are both active. Transaction T1 reads both and sees two; T2 reads both and sees two; T1 disables A; T2 disables B; both commit under snapshot isolation without a shared write conflict. The invariant “at least one active worker” fails. Serialize the decision using one coordinating row or use serializable isolation with whole-transaction retries.

Transfer: does a mutex around one Python dictionary fix both database races?

Only for callers that actually share and obey that mutex in one process. Another process, script, or server bypasses it. Protect the invariant at the shared authoritative boundary and test concurrent database sessions.
