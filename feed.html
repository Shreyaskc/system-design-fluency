LESSON 15 / 27 · ORIGINAL TEACHING EXAMPLES

Case 2 · A useful neighborhood feed

Corner Market now lets residents follow sellers and neighborhood groups. A feed is a prepared or computed list of candidate posts. The central choice is when to do the work: when someone publishes or when someone reads.

Exact interview prompt

Design a home feed showing recent posts from followed sellers and groups. Handle a few accounts with millions of followers without making normal publishing slow.

Clarifying questions and assumed answers

Ask whether the feed is chronological or personalized. Start with reverse chronological order; introduce relevance later. Assume 1 million daily active users, 100 followed authors per user on average, public posts with block and takedown rules, 30-day feed history, and 20 cards/page. Users publish 0.2 posts/day on average. A daily active user is one who uses the app that day; it is not the number simultaneously connected. Exclude comments and ads from the first design. A new post may take five seconds to appear, but blocked or deleted content must be filtered at read time. Freshness and visibility correctness have different requirements.

Propose feed p95 server latency under 250 ms and 99.9% monthly availability, with graceful stale results during fanout failure. Fanout means distributing one post reference into many recipients' inboxes. Publishing must acknowledge after durable storage without waiting for every recipient. No promise of an exact immutable feed snapshot across changing moderation rules.

Capacity and its implications

At 1 million users × 20 page requests/day, there are 20 million page reads/day, about 231.5/s average and 2,315/s at assumed 10× peak. At 20 cards/page this is 400 million card impressions/day. Publication volume is 200,000 posts/day ≈ 2.31/s average. If each author has 100 recipients on average, push fanout produces 20 million inbox inserts/day ≈ 231.5/s average; retention of 30 days gives 600 million references. At 32 logical bytes/reference that is 19.2 GB before indexes, storage layout, and replicas. These averages hide the important tail: one author with 2 million followers produces 2 million inserts per post.

At an explicitly assumed sustained worker throughput of 10,000 inserts/s across a pool, that one post requires 200 seconds, exceeding five-second freshness. This is a planning calculation, not a benchmark. It motivates separating high-fanout authors or changing worker capacity; it does not prove one database technology is slow.

Progressive design

Start with pull: on a feed request, query recent posts for followed authors using an index beginning with author_id and ordered by time. Merge a bounded number of recent results. This avoids copying data and is easy to reason about. Measure the cost of following hundreds or thousands of authors before moving to push fanout.

Then push references, not duplicated post bodies, into active users' inboxes. An outbox is a table of pending integration events written in the same database transaction as domain data. A dispatcher sends its rows to a queue. If it crashes after sending but before marking dispatched, it sends again; unique (user_id, post_id) makes repeated inserts harmless. Persist an event cursor so fanout can resume after a partial recipient batch.

Use a hybrid for large authors: read their latest posts at request time and merge with the materialized inbox. Materialized means precomputed and stored. Choose the threshold from estimated recipient write cost, audience activity, freshness budget, and measured read cost, not a magical follower count. Deduplicate by post_id because migration between modes can put a post in both paths. New follows need a bounded history backfill; unfollows should be checked when reading until old references are removed.

Pagination and visibility deep dive

Order by (created_at, post_id), with post_id as a deterministic tie-breaker. An opaque signed cursor contains that pair and a feed session cutoff time. Request the next page strictly older than the last pair and not newer than the cutoff. Offset pagination shifts when new posts arrive and repeats items. A keyset cursor avoids that shift, although deleting or hiding posts can still shorten pages; oversample within a bounded limit and report exhaustion honestly.

Never treat a stale inbox reference as permission to show content. Batch-load current post status and evaluate blocks, group membership, and privacy. If the authorization dependency fails, fail closed for restricted content. For public content, the interviewer must approve any bounded stale policy. Deletions create tombstones, small records indicating removed content, and trigger asynchronous cleanup; read filtering provides the immediate correctness barrier.

Failures and operational tradeoffs

When the queue falls behind, durable posts still exist, so show a freshness indicator and optionally fall back to a bounded pull query. Put a budget on fallback concurrency: a queue incident should not become a database incident. When one account causes enormous fanout, isolate its work so ordinary authors are not starved. Retry with backoff, cap attempts, and move persistently failing events to a review queue with an audited replay procedure.

If the cache disappears, reduce page size or shed optional enrichment before increasing database pressure. If the follow graph is partitioned across stores, graph changes and fanout race: a post may arrive after an unfollow, which is why read-time filtering remains necessary. Store only the 30-day window, prune inactive inboxes, and reconstruct on return when write savings justify it.

Alternatives and evolution

Reject push-to-everyone as the universal design because celebrity writes dominate. Reject pull-everything as the universal design when wide follow graphs and repeated reads exceed the request budget. Neither is inherently wrong at small scale. A relevance model changes pagination: scores and candidate sets evolve, so freeze a ranked result window or use a session token rather than pretending time order still suffices. Keep a chronological fallback and measure relevance quality separately from system availability.

Monitor feed latency, end-to-end freshness, fanout backlog age, duplicate suppression, empty-feed rate, filtered-card rate, and per-author skew. Audit privacy failures as correctness incidents. Compare cost per thousand pages and per published post as traffic grows. Roll out hybrid changes by cohort and verify no missing or repeated posts with shadow reads.

Follow-ups and answer rubric

Practice: a user follows an author while their post is being fanned out. Must the post appear?

Define semantics first. Our assumed policy shows the author's recent public posts after follow. Backfill plus read-time merging covers the race; deduplicate IDs. A stricter publish-time membership snapshot would require versioned graph semantics.

Practice: a deleted post appears on page two from an old cursor.

The cursor determines ordering, not authorization. Current visibility filtering must remove the post on every page and every cache path.

Strong: derives hybrid fanout from skew, specifies resumable/idempotent work, and separates freshness from privacy. Weak: draws a queue without replay behavior, says “eventual consistency” to excuse deleted content, or uses offsets without discussing shifting pages. Principal depth includes cohort migration, per-tenant isolation, and cost/freshness controls.

Technical reference checked 2026-10-19: PostgreSQL unique constraints. Cursor, hybrid fanout, freshness targets, and workload figures are design assumptions rather than vendor guarantees.

A short spoken walkthrough

Candidate: Is the five-second freshness target also a promise to immediately hide blocked content?
Interviewer: Freshness may lag, but blocked content must be hidden.
Candidate: I will start with the simplest durable path and state the boundary before distributing it.
Interviewer: Your inbox already contains the post. Is deleting the source enough?
Candidate: No. The inbox is a derived list of IDs, not an authorization authority. I filter visibility at serving time and remove stale references asynchronously. If the authority is unavailable, I omit uncertain content rather than expose it. Feed completeness can degrade while the access boundary holds.
