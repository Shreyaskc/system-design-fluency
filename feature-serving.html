LESSON 23 / 27 · ORIGINAL TEACHING EXAMPLES

Elective: reliable AI recommendations and feature serving

Worked interview • data freshness and safe fallback • 45 minutes

Exact prompt and scope

Exact prompt: “Corner Market wants personalized product recommendations. Design the feature and inference serving path, including training consistency, freshness, failure behavior, and safe rollout.” A feature is a measurable input to a model, such as a customer's seven-day category-view count. Inference is applying a trained model to inputs to obtain a prediction. This elective follows analytics because it reuses event collection, replay, and freshness reasoning; it is not a requirement to add artificial intelligence to every system.

  • What outcome? Assume rank up to 200 eligible candidate products and return 20. Candidate generation chooses a smaller relevant set; ranking orders that set.
  • What model? Assume a compact CPU-served ranking model, not a large language model. Model training research and graphics-processor infrastructure are outside this interview's scope.
  • What quality contract? Assume experiments evaluate useful purchases and user experience, with guardrails for errors, latency, stale inventory, and merchant concentration. No guaranteed business uplift is claimed.
  • Which data? Assume consented product interactions and current catalog eligibility. Never use payment credentials or sensitive personal attributes as features.

Capacity, latency, and freshness

Assume 100,000 daily shoppers request 20 recommendation panels/day: 2,000,000 requests/day, or 23.15 requests/second average. Tenfold peak is 232/second after rounding upward. At 200 candidates/request, peak scoring demand is 46,400 candidate scores/second. Benchmark the actual model and batch shape; this arithmetic does not determine how many CPU cores are sufficient.

Assume 20 user features at 8 bytes each for 100,000 users: 16 MB raw numeric values. Forty thousand products with 30 eight-byte features require 9.6 MB raw. Keys, missing-value indicators, timestamps, versions, replicas, serialization, and indexes add overhead. Fetching 200 candidate vectors separately would produce 46,400 remote lookups/second at peak. Batch reads and compact cached item features reduce remote call count; monitor payload size as well as calls.

Set a proposed 99th-percentile response target of 150 milliseconds. A sequential budget might allocate 10 ms gateway/network overhead, 20 ms candidate retrieval, 25 ms feature retrieval, 40 ms inference, 15 ms eligibility filtering and response, plus 40 ms reserve. These sum to 150 ms but do not prove the system's 99th percentile: component tails correlate, network conditions vary, and end-to-end load tests are required. Assume user interaction features should be less than five minutes old, catalog availability less than one minute old, and recommendations may fall back safely if these goals are missed.

A model manifest declares the required inputs; deployments must reject incompatible feature versions. Do not expose unnecessary user features in the client response. An exposure event records what the user actually saw, so offline evaluation can distinguish unseen candidates from displayed results. Restrict access to feature data and bound retention independently for raw events, derived features, and experiment logs.

Progressive design: earn the model

Start with a nonpersonalized baseline: available popular items by neighborhood and category, with explicit merchant and safety rules. It establishes an availability fallback and a measurable comparison. Add offline-trained ranking only when the product question and evaluation data justify it. Keep catalog eligibility authoritative outside the model: a high predicted score never authorizes sale of unavailable stock, bypasses access rules, or overrides a merchant's removal.

Generate candidates using simple category and popularity indexes first. Fetch user features once and item features in a batch; cache shared item vectors with versioned keys. Score the candidate batch within a bounded deadline and filter current eligibility before responding. If fewer than 20 remain, fill from the safe baseline or return fewer, according to the user experience contract. Avoid unlimited retries that exceed the request's deadline.

Feature freshness requires two timestamps. source_event_time indicates the newest source fact incorporated; computed_at indicates processing time. Recomputing from yesterday's input now produces a recent computation timestamp with stale information. Check the appropriate freshness measure per feature. A missing feature and a measured zero are different values: include a missing indicator or a documented training-consistent default, and record how frequently defaults are used.

Training consistency and temporal leakage

Training-serving skew means training and online inference compute inputs differently. A seven-day count calculated in UTC during training and local days online is one example. Share versioned transformation logic where practical, test with fixed event sequences, and compare sampled online feature values with offline recomputation. A shared codebase alone does not guarantee identical data arrival, window boundaries, or missing-value behavior.

Point-in-time correctness means constructing each training row only from information available at that row's prediction time, subject to the system's actual availability contract. If a shopper was scored at 10:00, a purchase at 10:05 must not enter that score's features. Late-arriving historical data can also leak knowledge if a backfill uses facts not available online at 10:00. Keep event time and availability time where the use case needs both. Join features as of the example timestamp and preserve labels separately.

Use time-based evaluation splits when predicting future behavior, avoid users or sessions accidentally leaking between incompatible splits, and compare against the baseline. Offline ranking metrics are proxies; run a controlled experiment with stable assignment and latency/error guardrails before broad release. Statistical methodology belongs in a dedicated experiment lesson, but the architecture must capture assignment, exposure, outcome, and model version so analysis is possible.

Failures and rollout

If the online store fails, use bounded cached features only within their declared freshness window or fall back to popular eligible items. If inference exceeds its deadline, return fallback and count the timeout. Do not silently serve arbitrary default vectors for every user and call the resulting output personalized. Track fallback rate, feature age, missing-feature rate, schema rejection, batch size, inference latency, and output score distributions.

Deploy a model and its compatible feature set together through a manifest. Preload artifacts, validate checksum and schema, warm instances, and route a small fraction of traffic before expansion. Shadow mode computes predictions without changing the displayed result; it helps measure latency and output differences but does not measure actual user response to the shadow output. Canary rollout exposes a small real audience and therefore requires business guardrails. Keep the previous compatible artifact and feature contract for rollback.

A traffic spike can overwhelm feature storage before model CPUs. Apply admission controls, cap candidates, batch reads, and degrade in a measured order. Cache keys containing only user ID can accidentally mix model or feature versions; include the relevant version and context. Limit cache lifetime for personalization, and prevent cross-user cache leakage through authenticated key construction. A feature pipeline outage should not make checkout unavailable: recommendation and purchase correctness have different dependency budgets.

Alternatives, evolution, and interview close

Reject a synchronous full-history warehouse query on every recommendation request: it moves large scans into a tight latency budget. Reject adding a vector database merely because the feature is called AI; ordinary indexed candidate retrieval may satisfy this compact model. Embedding retrieval becomes justified when learned similarity improves candidate quality under measured cost and latency. Reject running a large generative model for this assumed ranking workload without evidence of benefit.

At multi-region scale, replicate relatively stable item features, route user state deliberately, and document freshness during pipeline partitions. Keep model artifacts identical by digest, but allow controlled regional rollouts. Cost includes feature computation, online reads, model execution, experiment logging, retraining, and operational support. Compare benefit with the popular baseline and remove complexity that fails to earn its cost.

Practice: offline accuracy improves dramatically after a backfill, but online results do not. What do you inspect?

Check temporal leakage, availability-time joins, changed metric definitions, selection bias, feature defaults, train/serve transformations, and exposure logging. Reconstruct a historical request using only data actually available then. A larger model is not the first repair.

Follow-ups and rubric

Follow-ups: How do deletion requests propagate? What does a safe fallback show? How do you roll back incompatible inputs? Strong: defines freshness and feature versions, separates eligibility from prediction, identifies leakage, and includes a baseline. Weak: adds a vector database without a retrieval requirement, treats recent computation as fresh data, or claims offline accuracy proves business impact.

A short spoken walkthrough

Candidate: May recommendations fall back when features are too old?
Interviewer: Yes, use a safe non-personalized list.
Candidate: I will start with the simplest durable path and state the boundary before distributing it.
Interviewer: Your latency is excellent but the model quality falls. What do you change first?
Candidate: I inspect feature age, missingness, model/schema version and training-serving agreement. Adding replicas does not repair wrong inputs. I canary the model and transformation together with quality and latency guardrails, then roll back the versioned bundle if they regress. Eligibility remains an authoritative filter, independent of model scores.
