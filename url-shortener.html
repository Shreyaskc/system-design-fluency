LESSON 14 / 27 · ORIGINAL TEACHING EXAMPLES

Case 1 · Share a neighborhood listing

Build the smallest reliable doorway into Corner Market, a fictional neighborhood marketplace. This case trains requirement selection, key allocation, caching, and abuse handling. All numbers are interview assumptions, not claims about a real business.

Exact interview prompt

Design a URL shortener so sellers can share Corner Market listings. Explain how you avoid duplicate codes, keep redirects fast, and remove dangerous links.

Clarify before drawing

Ask: arbitrary websites or only our listings? Assume both, with malware controls. Can destinations change? Assume immutable destinations; owners may disable links. Are aliases required? Optional custom aliases are in scope. Anonymous creation? No; authenticated sellers only. Is a short link a secret? No. Do we need exact click counts? Approximate daily analytics suffice. Retain mappings for one year. A removed or expired code is never reassigned within the retention period.

Set nonfunctional requirements: redirect service availability objective 99.95% monthly, redirect server-side p95 latency under 100 ms in the primary region, and owner creation response p95 under 300 ms. A percentile means the stated fraction of observations fall below that value. These are proposed objectives to validate with the interviewer and load tests; network time is separate. Disable propagation must complete within 60 seconds, so cache policy is part of the correctness contract.

Estimate with units

Assume 1 million new links/day and 100 million redirects/day; decimal units throughout. Average creation rate is 1,000,000 / 86,400 ≈ 11.6 writes/s. Redirect rate is approximately 1,157/s. With an assumed 10× peak, provision and test 116 writes/s and 11,574 redirects/s. A 500-byte logical mapping costs 500 MB/day, or 182.5 GB/year before indexes, replicas, database overhead, and backups. Three complete copies alone require 547.5 GB. A 90% cache hit rate leaves about 1,158 peak database reads/s, but a cold cache must survive much more.

Use 10 random base62 characters: 62 choices per character gives 6210 ≈ 8.39 × 1017 possible codes. At 365 million stored links, the approximate probability that a fresh candidate collides is n/N ≈ 4.35 × 10−10. This does not mean no collision ever occurs; birthday effects accumulate across all draws. A unique database constraint, with bounded retry on conflict, is the actual guarantee.

Contract and data model

POST /v1/links
Idempotency-Key: seller-generated-request-id
{ "destination": "https://example.test/item/42", "alias": null }
201 { "code": "k8W1pZ3aQx", "short_url": "https://s.example.test/k8W1pZ3aQx" }
GET /k8W1pZ3aQx  → 302, Location: validated destination
DELETE /v1/links/k8W1pZ3aQx → 204 (owner only)

links(code PRIMARY KEY, owner_id, destination, status,
      created_at, expires_at, version)
requests(owner_id, idempotency_key, request_hash, code,
         UNIQUE(owner_id, idempotency_key))

An idempotency key identifies one intended operation across retries. Store its response and request hash in the same transaction as the mapping; a reused key with different input returns conflict. Let the database decide alias uniqueness atomically. Checking availability then inserting is vulnerable to two concurrent requests.

Labeled architecture and progressive design

CREATE: Seller → API/auth → mapping database + request record
REDIRECT: Browser → edge/load balancer → redirect service → cache
                                                  miss ↓
                                             mapping database
ANALYTICS: redirect service → bounded event buffer → daily aggregation
DISABLE: Owner → API → status update → invalidation + expiry fallback

First deliver a single service and relational database with an indexed primary-key lookup. Add multiple stateless redirect instances when measured demand warrants them. A cache stores frequently requested mappings for at most 30 seconds. A time to live (TTL) is the maximum cache residence duration. Always check expiry and status in cached data. Use short-lived negative caching for missing codes to reduce random-code attacks, but invalidate negative entries when a custom alias is created. Never let analytics determine whether the redirect succeeds.

Choose a temporary 302 redirect and explicit cache directives because owners can disable links. A permanent redirect may remain cached in clients beyond your purge control. The 60-second disable promise requires bounding every participating cache, including an edge cache if added. Sensitive or urgent takedowns may need a small denylist checked before normal cache lookup. Explain the availability cost of making that check authoritative.

Deep dives and failure analysis

A viral link is a hot key: one key receives a disproportionate share of requests. Replicating that small mapping across service caches reduces database load; merely sharding the database does not spread reads for one code. Coalesce concurrent misses so one request loads a mapping and others wait briefly. Randomize refresh times without extending the maximum takedown budget. A stale cache cannot prove that a link remains non-revoked: never extend an entry beyond the stated revocation deadline without checking the authority. Include replica lag and refill races in that deadline; use versioned invalidation or authoritative revocation checks if the required bound cannot otherwise be met. Negative lookup traffic still needs per-client limits and bounded cache admission.

On a database outage, serve eligible cached mappings until their allowed lifetime expires; return a retryable 503 for unknown mappings rather than falsely saying they do not exist. A read replica can reduce load but replication lag may make a newly created link appear absent; route recent creation reads to the primary or seed cache after commit, with a primary fallback on a miss. A cache outage must trigger concurrency limits, not an uncontrolled database stampede.

Do not fetch arbitrary destinations synchronously from unrestricted servers. Validate supported schemes, reject control characters, use safe redirect header construction, and isolate any malware fetcher with network restrictions against internal addresses and redirects to them. This prevents server-side request forgery when a scanner visits attacker-chosen URLs. Track abuse reports and audit disable actions without logging secret query strings unnecessarily.

Alternatives, operations, and evolution

A monotonically increasing integer encoded in base62 is simpler but exposes enumeration; adding obscurity is not authorization. Hashing the long URL does not remove collisions and creates policy questions about ownership and destination normalization. A global distributed key service is unnecessary for this workload unless allocation becomes a measured bottleneck. Start in one write region with backups and restore drills; multi-region reads can follow. Multi-region writes need collision enforcement and an explicit conflict policy for custom aliases.

Monitor redirect success and latency, cache hit rate, primary fallback rate, collision retries, disable propagation, and analytics event loss. Sample logs; billions of full request logs can cost more than mappings. Add capacity before cache cold-start tests exceed the database budget. Partition old mappings by retention only after examining lookup and expiration costs.

Interviewer follow-ups and rubric

Practice: two sellers request the same alias at the same time. What happens?

The unique constraint accepts one transaction. The loser receives 409 and can choose another alias. Its idempotency record must not claim success. Retrying the winner's original key returns the original response.

Practice: analytics must become billing-grade. What changes?

Define which redirects count, durable event acceptance, stable event IDs, deduplication, reconciliation, and an explicit behavior when the event path is unavailable. The earlier lossy buffer no longer meets requirements.

Strong answer: ties temporary redirects and TTL to revocation, calculates rates, distinguishes collision probability from uniqueness enforcement, and bounds cache failures. Weak answer: says “use Redis and hashing” without atomic allocation, deletion behavior, or an overload plan. Principal depth includes abuse ownership, regional failure policy, and measurable rollout criteria.

Technical reference checked 2026-10-19: PostgreSQL constraints for atomic uniqueness; HTTP semantics, RFC 9110 for redirect behavior. The workload and design choices above are original assumptions.

A short spoken walkthrough

Candidate: Must takedown be immediate, or may cached links resolve briefly?
Interviewer: Assume a 60-second maximum.
Candidate: I will start with the simplest durable path and state the boundary before distributing it.
Interviewer: Why not use a permanent redirect for performance?
Candidate: A browser may retain it beyond our takedown control. I choose a temporary redirect and bounded cache policy, including refill and replica lag. If you change the requirement to immediate takedown, I must validate revocation authoritatively on each resolution or use a delivery layer that can enforce the new contract.

This is the compact interview explanation. The earlier sections expand the mechanism and failure traces; adapt the time spent on them to the interviewer’s direction.
