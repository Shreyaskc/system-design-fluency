9. Define reliability from the shopper outward

Measure a useful outcome

Reliability is delivering the promised behavior despite ordinary faults and change. A SLI measures an outcome; a SLO sets its target. For Corner Market, define a good catalog request as an eligible request returning a correct, authorized result within 300 milliseconds. Separately measure successful eligible reservations and duplicate payment captures. A health check returning 200 is not proof that a shopper can complete checkout.

Define the denominator, observation point, exclusions, and measurement window before writing a percentage. A client-side measure includes failures before the server sees a request; server logs alone cannot count them. The Google SRE chapter on service level objectives, checked 2026-10-19, distinguishes indicators, objectives, and agreements. The objectives here are illustrative teaching choices, not recommended universal targets.

Budgets and dependency arithmetic

If 600,000 eligible checkout requests occur in a thirty-day window, a 99.9 percent request-success objective permits 600 bad requests. A time-based 99.9 percent objective over thirty days permits 43.2 minutes of failure because 30 × 24 × 60 × 0.001 = 43.2. Request and time budgets differ when traffic is uneven. Do not interchange them. An error budget is the allowed imperfection implied by the objective; it supports explicit release and reliability decisions.

Suppose a request requires three independently available dependencies, each available 99.9 percent of the time. Under that simplifying independence assumption, all three are available approximately 0.999 cubed, or 99.7003 percent. Shared network or identity failures violate independence and may be worse. Reduce required dependencies by making email asynchronous, storing necessary local state, or degrading optional recommendations. Replicating every component without examining shared failure causes can leave the same weakness intact.

Prevent overload from becoming collapse

A timeout caps waiting; a circuit breaker temporarily stops calls to a failing dependency; a bulkhead limits one class of work so it cannot exhaust all resources. Configure each around the customer contract. Bound database connection pools and request queues. When the system is saturated, reject some new work promptly with retry guidance rather than allowing every request to time out while consuming memory. Retried work is still work: three retries can multiply offered traffic precisely when capacity is weakest.

Degradation should be intentional. Serve a cached product description with visible freshness when allowed, omit optional recommendations, and disable new checkout if inventory correctness cannot be preserved. Avoid returning “order failed” after a payment timeout when the actual outcome is unknown. Persist a pending state and reconcile. Make support tools able to locate the attempt by a nonsecret identifier.

Observe causes and consequences

Metrics are numerical measurements over time; logs are individual event records; traces connect steps across a request. Track request rate, errors, duration, saturation, database lock waits, replica lag, queue age, and business invariant violations. Use stable correlation identifiers without embedding personal data. High-cardinality labels such as raw shopper identifiers can overwhelm metric systems and expose sensitive information. Sample traces carefully so rare errors and slow paths remain diagnosable.

Alert on user impact or imminent loss of a critical promise. A high CPU reading may be healthy utilization; a rising duplicate-capture count deserves immediate attention even when CPU is low. Build runbooks with safe first actions, verification queries, escalation ownership, and rollback instructions. Run a restore exercise and a dependency-outage exercise before claiming recovery readiness. A backup job's success signal is weaker evidence than a verified restoration.

Security belongs in the data flow

Identify trust boundaries: client to gateway, service to database, workers to payment provider, and operator to administration tools. Authenticate identity, authorize each object access, encrypt transport, minimize stored secrets, and grant each service only necessary permissions. Treat uploaded files and search text as untrusted input. Validate content and size; avoid using unchecked user input as a network destination. An upload service fetching an arbitrary URL can become a path into private networks.

Keep public catalog data separate from private orders. Redact credentials and payment details from logs. Define retention and deletion policies with qualified business and legal owners rather than inventing universal compliance rules. Audit privileged actions and test revoked access. A design diagram should show both ordinary traffic and administrative paths because maintenance interfaces often bypass assumptions made for the public API.

Practice: checkout availability improves, but support sees more charged-without-order complaints. Is the release successful?

No conclusion follows from availability alone. Investigate the payment/order invariant, uncertain attempts, and reconciliation lag. A faster acknowledgment that hides an inconsistent business outcome can improve a narrow metric while harming shoppers. Rollback or disable the risky path based on the correctness impact.

Exit artifact: define two user-facing indicators and one invariant alarm, then explain the first five minutes of response to each breach.

Request trace: Authorized recovery

A shopper requests order O; the service checks identity and O ownership before reading details; a database timeout triggers bounded retry. If an operator later investigates, the support path must enforce its own permission and audit checks. Reliability recovery never grants permission to expose another shopper’s order.
