LESSON 18 / 27 · ORIGINAL TEACHING EXAMPLES

Case 5 · Find the right bicycle

Listen to this chapter →

Residents want “blue bicycle under 200 nearby,” not every row containing those letters. Search separates transactional truth, a derived retrieval index, and relevance quality. A fast result that exposes a removed listing is still wrong.

Exact interview prompt

Design listing search for Corner Market with text, category, price, and distance filters. New listings should appear quickly. Explain indexing, pagination, relevance, and behavior when the search cluster fails.

Clarifications and assumptions

Assume 10 million active public listings, 1 million new or updated listings/day, and 10 million searches/day. Text is short titles and descriptions; no web crawling. Include exact category/price filters and geographic radius; defer semantic vector search until evidence shows a need. Ask how sold or private listings behave: authoritative eligibility must be checked before display and again before reservation. New listings should become searchable within 30 seconds at p95; removed listings must stop appearing within five seconds under healthy dependencies. If the authoritative eligibility check is unavailable, suppress uncertain results.

Propose 99.9% monthly search availability and server-side p95 latency under 300 ms. These are negotiated targets, not inherent engine properties. Search freshness is separate from write success: the listing creation response confirms database commit, with a “search indexing pending” state if necessary. Do not promise immediate search visibility from a successful database write.

Calculate workload

10 million searches/day / 86,400 ≈ 115.7 queries/s average, and 1,157/s at assumed 10× peak. Updates average 11.6/s and peak at 116/s under the same factor. At an assumed 2 KB searchable document, raw document content is 20 GB; an assumed 3× indexing expansion gives 60 GB for one complete index copy. One replica doubles this to 120 GB, before spare capacity and segment merge overhead. A full blue-green rebuild temporarily needs both old and new index generations: at least 240 GB under these simplifying assumptions.

If a worker indexes an assumed measured 1,000 documents/s, rebuilding 10 million documents requires 10,000 seconds, about 2.78 hours before catch-up and verification. The number is an explicit planning assumption. Benchmark real mappings and analyzers: token count, field cardinality, and update frequency affect storage and throughput substantially.

Progressive design

For an early product, a relational database with proper text search and indexes can satisfy modest scale with fewer moving parts. Once retrieval features, query load, or ranking experimentation justify separation, add a search index as a rebuildable derived view. A derived view stores data computed from an authoritative source. It is not the transaction system for inventory or payment decisions.

An inverted index maps a normalized term to the documents containing it. An analyzer transforms text into terms through tokenization and optional normalization. Test how “bikes,” “bike,” punctuation, and multiple languages behave; blindly stemming product model names can damage precision. Precision measures how many retrieved results are relevant; recall measures how much relevant material was retrieved. Neither equals service latency.

The listing transaction writes an outbox event with a monotonically increasing listing version. A dispatcher retries delivery; the indexer ignores older versions so delayed updates cannot overwrite new content. Represent deletions as versioned tombstones and retain them long enough to cover possible replay. A fresh index rebuild must also honor changes after its snapshot watermark. Otherwise a deleted listing can reappear after cutover.

Retrieval, ranking, and pagination

Apply structured price, currency, category, status, and distance constraints as filters. Rank remaining candidates using text relevance plus carefully bounded product signals such as recency or distance. State where ranking is applied: candidate retrieval followed by optional reranking of a bounded set. A reranker cannot recover relevant items excluded by retrieval. Use minimum query length, bounded radius, bounded page size, and timeouts to limit expensive queries and abuse.

For stable pagination, return an opaque cursor containing the sort tuple and a bounded search-session or point-in-time identifier if the engine supports it. A point-in-time view fixes the index state for a search session; it consumes resources and expires. Use a deterministic ID tie-breaker after relevance score. Explain expired cursors explicitly and restart the query. Deep numeric offsets require work over discarded results and shift under updates; avoid offering unlimited page numbers.

Hydrate candidates in one bounded batch instead of one database call per hit. Recheck current public/sold/deleted eligibility and authorization against a reliable source or a tightly controlled revocation mechanism. Oversample to fill a page after filtering, but cap rounds and total candidates. A total-hit count from a stale search view can differ from currently displayable listings; label it approximate or omit it.

Failure and correctness analysis

If indexing stalls, keep accepting listing writes while exposing freshness and alerting on oldest unprocessed event age. If the search cluster fails, return a deliberately limited recent/category browse view if the database has capacity; do not silently run unbounded wildcard SQL across 10 million rows. Protect fallback with concurrency limits and its own latency budget. Search availability may be lower than listing-write availability; that is an explicit product tradeoff.

If a shard is unavailable, decide whether partial results are acceptable and mark them. A shard is one partition of the index. Replicas improve read availability but a correlated deployment or zone failure can still affect both if placement is poor. During a hot query surge, cache public query results with bounded freshness and eligibility filtering. Do not put precise personal locations in shared cache keys or broad logs unnecessarily.

Alternatives, operations, and evolution

Reject treating the search index as the sole source of sold status: indexing lag violates reservation correctness. Reject adding embeddings by default; measure failed queries, relevance, language needs, latency, and cost first. If semantic retrieval is added, combine its candidates with lexical retrieval, evaluate with judged queries, and preserve exact filters. A plausible synonym can be wrong for a specific spare part.

Monitor query p95/p99, error rate, zero-result rate, index lag, eligibility filtering rate, rejected expensive queries, shard size skew, and rebuild duration. Evaluate relevance with a versioned set of representative judged queries, including rare and multilingual terms. A/B experiments need guardrails for irrelevant results, seller fairness, and latency. Rebuild using snapshot plus replay, compare counts and sampled documents, shadow representative queries, then switch an alias atomically with a rollback plan. Avoid changing database schema and index generation in an incompatible single step.

Follow-ups and rubric

Practice: version 12 arrives before version 11, then a delete at 13. What should remain?

Accept 12, ignore 11, then record the deletion at 13. Replaying 12 must not resurrect the document. Tombstone retention and rebuild watermarks must cover the supported replay window.

Practice: the index says a bicycle is available. Can checkout reserve it?

No. Search supplies candidates. The reservation service checks authoritative current inventory and commits the reservation transaction; the result page is not a lock.

Strong: explains derivation and replay, separates relevance from correctness, and makes filtering and rebuild cutover concrete. Weak: names Elasticsearch without update semantics, claims indexes are immediately current, or uses search as inventory truth. Principal depth includes relevance evaluation, migration rollback, fallback budgets, and privacy-aware observability.

Technical references checked 2026-10-19: Elastic near-real-time search; PostgreSQL full text search. Refresh timing and engine-specific point-in-time APIs must be verified for the deployed version; our 30-second freshness objective is an application requirement.

A short spoken walkthrough

Candidate: May results lag price and stock updates?
Interviewer: Yes, but checkout must validate current price and inventory.
Candidate: I will start with the simplest durable path and state the boundary before distributing it.
Interviewer: Why not query the search index when reserving stock?
Candidate: It is a derived view and may lag or replay out of order. I use it for candidate retrieval, then the authoritative order transaction validates the quote and available units. If search fails, a narrow database-backed catalog fallback may be acceptable, but it cannot silently promise the same ranking or throughput.
