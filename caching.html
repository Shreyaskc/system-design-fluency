5. Cache with a freshness and failure contract

Listen to this chapter →

A cache is a disposable copy

A cache stores data closer to its consumer or in a faster medium to reduce latency or repeated computation. It creates another version of reality. Corner Market can cache product descriptions because a short delay is tolerable; the final stock reservation still consults authoritative inventory. First define the maximum acceptable staleness, key ownership, invalidation mechanism, eviction behavior, and what happens when the cache disappears. A cache that is necessary to reconstruct purchases is functioning as a database and needs a different durability contract.

In cache-aside, the application checks a key, reads the database on a miss, and populates the cache. A hit returns the cached value. A TTL bounds an entry's residence time, not necessarily the age of the underlying fact if a stale source repopulates it. Use versioned product values and include the version in invalidation messages. Keep shopper-private results out of shared public keys; include tenant, authorization scope, language, and other response-shaping inputs where appropriate.

Calculate benefit and failure load

At the foundation baseline peak of 231.5 catalog requests/second, a ninety-percent hit ratio leaves approximately 23.15 database reads/second, assuming one database read per miss. If hits take 2 milliseconds and misses 20 milliseconds, the weighted mean lookup time is 0.9 × 2 + 0.1 × 20 = 3.8 milliseconds. That arithmetic does not predict p99 latency, because ten percent of requests still follow the slow path. Network time and application work are excluded from this illustrative calculation.

On complete cache failure, database load returns to 231.5 reads/second, ten times the warmed miss load. Provision that fallback capacity or deliberately shed some traffic. A cache miss storm occurs when many callers simultaneously refill the same missing data. Coalesce concurrent misses so one caller fetches while others await the same result. Add small random variation to expiration times to avoid synchronized expiry of an entire catalog. Bound refill concurrency so database survival takes priority over hit-ratio recovery.

Invalidate without hand-waving

Suppose reader A misses, reads old price version twelve, and pauses. Writer B commits version thirteen and deletes the cache key. Reader A then fills version twelve after the delete. “Delete on every write” did not prevent stale resurrection. A short TTL bounds this particular stale fill, but strict freshness needs a stronger mechanism: compare versions against a retained current-version marker when populating (not merely against the cached value, which may be absent). Keep a version tombstone beyond the maximum stale-reader lifetime, and atomically reject any refill older than that marker; otherwise eviction or deletion can erase the fence and permit stale resurrection. If that lifetime cannot be bounded, validate against the authority rather than claiming a strict freshness guarantee. Other options include using versioned immutable keys with an authoritative current-version pointer, or bypass the cache for the critical operation. Each mechanism has a coordination cost.

Write-through updates the backing store through a controlled path that also updates the cache. Write-behind acknowledges a cache update before later persistence and risks loss or reordering unless backed by durable machinery. Name the actual acknowledgment boundary; the label alone proves nothing. An event-driven invalidation channel may lag or lose an invalidation, so combine it with bounded expiration and monitoring when the freshness contract allows that compromise. Redis describes server-assisted client cache invalidation in its client-side caching documentation, checked 2026-10-19; that mechanism still needs application failure handling.

Choose what to cache

Cache immutable image variants at a content delivery network, which serves bytes near clients. Use a filename derived from content or version so updated images have a new address. Cache catalog fragments with explicit freshness. Avoid shared caching of payment status unless the key and response policy preserve authorization and the product accepts delay. Negative caching stores a not-found result briefly; it reduces repeated misses but can hide a newly created object until expiry. Limit its duration and distinguish a genuine absence from a temporary database failure.

A cache eviction policy chooses entries to discard under pressure. Least recently used approximates the belief that recently accessed objects are likely to be accessed again. A scan through millions of cold items can still evict valuable entries. Observe hit ratio by endpoint, object size, refill latency, eviction rate, and source load. A ninety-nine-percent global hit ratio can conceal a business-critical endpoint with no useful hits.

Practice: should checkout trust a cached price that is forty seconds old?

Only if the business contract explicitly promises that price or accepts that age. A safer baseline submits the observed price version; the server checks its authoritative value and either honors a documented quote or asks for confirmation of the change. Cache freshness and customer consent are separate decisions.

Exit artifact: describe one stale-fill race on a timeline, then demonstrate how your selected mitigation preserves the stated freshness bound. Do not claim instantaneous invalidation unless every relevant race and failure path supports it.

Request trace: Authoritative price at purchase

A catalog request hits price version twelve; checkout submits that version; inventory checks the authoritative quote; a changed price triggers explicit reconfirmation. If invalidation is delayed, browsing may be stale but the purchase promise remains protected. Choose cache-aside for browsing because the sixty-second freshness allowance permits a bounded stale view.
