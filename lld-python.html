11. Implement the boundary: Python and low-level design

Listen to this chapter →

Make the promise executable

Low-level design turns system promises into interfaces, data structures, state transitions, and tests. Start with one narrow component rather than a hierarchy of speculative classes. Corner Market needs a reservation service whose public operation either creates one hold, returns the existing result for a repeated request, or explains a business rejection. Inject a clock so expiry tests do not sleep, and inject persistence so concurrency assumptions are visible. An in-memory implementation teaches interfaces but is not evidence of distributed correctness.

from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class ReserveCommand:
    shopper_id: str
    request_key: str
    store_id: str
    item_id: str
    quantity: int

class ReservationRepository(Protocol):
    def reserve_once(self, command: ReserveCommand, now: float) -> str:
        """Atomically deduplicate, check stock, and create one hold."""
        ...

class ReservationService:
    def __init__(self, repository, clock):
        self.repository = repository
        self.clock = clock

    def reserve(self, command):
        if not 1 <= command.quantity <= 100:
            raise ValueError("quantity outside supported range")
        return self.repository.reserve_once(command, self.clock())

The repository contract is deliberately strong: it must implement all listed effects atomically, compare repeated request bodies, and return the original result when appropriate. Splitting these into independent repository calls would leak a race into the service. A production implementation uses a database transaction and unique constraint, not a Python dictionary shared by several servers. Use wall-clock timestamps for business deadlines, with a documented authority; use a monotonic clock for local elapsed durations so clock adjustments do not refill tokens backward.

Exercise one: deterministic token bucket

A token bucket admits bursts while limiting sustained request rate. It stores capacity, refill rate, available tokens, and last observed time. On each request, compute elapsed time, refill up to capacity, then spend one token if available. With capacity ten and refill two tokens/second, an idle bucket admits ten immediate requests; an eleventh is rejected; after half a second one token is available. The check and decrement must be atomic under concurrent callers.

Reveal implementation outline and tests

Use tokens = min(capacity, tokens + max(0, now - last) * rate); update the effective last time without allowing it to move backward; spend only when tokens are at least one. Inject a monotonic clock. Test initial burst, fractional refill, cap after long idle, simultaneous calls, and backward-time input to the pure model. For multiple servers, either centrally coordinate updates or explicitly accept a bounded per-instance overshoot. A process-local lock protects threads in one process, not a fleet.

Exercise two: a reservation state machine

Model states HELD, CONFIRMED, and EXPIRED. A transition function takes the current state, command, authoritative time, and deadline. Confirm succeeds only while held and before the deadline; expire succeeds only while held and at or after it. Repeating a completed operation returns its stable result. Two concurrent operations must compare and update the version atomically. Choose the exact deadline boundary and apply it consistently rather than letting two code paths disagree about equality.

Reveal critical scenarios

Test confirm just before expiry, expire exactly at the deadline, confirm after expiry, repeated expire, repeated confirm, and a confirm-versus-expire race. Assert that quantity is returned at most once and cannot be both confirmed and returned. A transaction or compare-and-swap against the same reservation version chooses one winner. A test that only calls methods sequentially does not validate the race.

Exercise three: bounded asynchronous workers

Use a bounded asyncio.Queue(maxsize=100) and a fixed worker count to avoid creating one task per unbounded incoming item. A queue's put waits when its configured capacity is exhausted, and task_done and join support tracking completed queue work. Those mechanics are documented in Python's asyncio queues, checked 2026-10-19. The queue is process-local and does not survive a crash.

Reveal implementation review criteria

Each worker gets an item, performs a bounded operation, and calls task_done in a finally block after deliberately handling the outcome. task_done is queue bookkeeping, not proof of business success or a durable acknowledgment. On failure or cancellation, persist a terminal outcome or arrange an explicit retry/requeue before treating the work as handled; blindly calling it and discarding the exception can silently lose work. Handle cancellation and shutdown deliberately. Distinguish an attempted job from a successful business effect. Test a slow dependency, a failing item, a full queue, and shutdown with work pending. If durable delivery is required, replace the process-local queue with a persistent broker and preserve the acknowledgment and deduplication contract.

Design review before abstraction

Prefer explicit domain results such as OutOfStock, PriceChanged, and PendingPayment over catching every exception as “failed.” Separate validation, persistence, and external side effects so tests can target boundaries. Use composition when behavior varies, such as a retry policy or clock; avoid adding factories and inheritance only to decorate a simple function. Explain thread safety, process safety, and distributed safety separately. Each has a different sharing boundary.

Exit artifact: implement all three exercises locally, add meaningful race and failure tests, and explain one guarantee your code does not provide. The snippets are teaching contracts, not a deployable payment implementation. Passing unit tests demonstrates the tested model; it does not establish database, network, or regional behavior that the model omitted.

Predict the confirm-versus-expire race

Reservation R is HELD at version four. Confirm reads HELD just before the deadline; expiry reads HELD at the deadline; expiry changes R to EXPIRED and returns three units; confirm blindly changes R to CONFIRMED. Now the system sold stock it already returned. Require both operations to condition their transition on the same authoritative state and version, within the transaction that changes inventory. Only one wins. Define the deadline comparison using a shared clock policy, and treat a losing confirmation as a business rejection rather than overwriting the winning state.
